# ADR-050 — متن فروشنده برای هر عکس در run استخراج

تاریخ: ۴ نوامبر ۲۰۲۶. وضعیت: تصمیم فنی برش اول PZ-03 در [PILOT_ZERO_PLAN](../PILOT_ZERO_PLAN_2026-11-04.md) و [ADR-049](ADR-049-small-catalogue-pilot-path.md). قرارداد run همان [ADR-032](ADR-032-n8n-extraction-run-contract.md)، [ADR-033](ADR-033-n8n-run-photo-links.md)، [ADR-038](ADR-038-n8n-run-claim.md) و [ADR-039](ADR-039-extraction-quote-and-credit-hold.md) است. **هیچ درخواست واقعی به OpenAI، import در n8n، انتخاب این نسخه در پیکربندی یا مجوز فرستادن متن فروشنده با این ADR داده نمی‌شود.** این ADR شماره‌گذاری نسخه ویس در ADR-047 را تغییر می‌دهد.

## زمینه

بررسی ۴ نوامبر (R04) نشان داد کپشن عکس نادیده گرفته می‌شود و متن آزاد به onboarding می‌رود. سناریوی پذیرش ADR-049 می‌خواهد فروشنده عکس کیف را با «کیف روزمره؛ جنس پارچه؛ مشکی؛ ۳۵۰٬۰۰۰ تومان» بفرستد و همان متن به همان محصول برسد. مقصد مبهم نباید حدس زده شود و برای هر پیام نباید پردازش پولی جدا ساخته شود.

## تصمیم

۱. **متن به عکس بسته است، نه به محصول حدسی.** متن فروشنده درباره یک عکس از دو راه می‌آید: کپشن عکسی که به Batch می‌رود، و پیام متنی که Reply به همان عکس خود فروشنده است. Reply به عکس با کلید HMAC پیام (`source_message_key`، همان کلید رسید) پیدا می‌شود، پس فقط عکس همان گفتگو و همان Workspace پیدا می‌شود. متن بدون Reply به هیچ محصولی وصل نمی‌شود و ربات می‌گوید آن را در کپشن یا با Reply بفرستد. کپشن عکسی که Reply به کارت محصول است (ADR-041) نادیده می‌ماند. تا پایان شناخت برند، Reply به عکس مثل هر متن دیگر پاسخ پرسش onboarding است.

۲. **ذخیره:** ستون `assets.seller_text` با کلید Workspace (cast `WorkspaceEncrypted`، AAD `assets.seller_text`). کپشن تا دانلود عکس در `telegram_media_intakes.seller_text` با همان روش `file_ref` رمز می‌ماند و فقط هنگام ساخت asset تازه منتقل می‌شود. همان بایت عکس دوباره متن اول را نگه می‌دارد و رسید می‌گوید متن پیام دوم ثبت نشد و باید روی پیام اول Reply شود. حذف حساب سطرهای هر دو جدول را پاک می‌کند. سقف یک عکس ۱۰۰۰ نویسه (code point) است؛ متن بلندتر کامل رد می‌شود، کوتاه نمی‌شود.

۳. **Reply دوم اضافه می‌شود:** متن تازه با خط جدید به متن قبلی همان عکس افزوده می‌شود. با قفل سطر asset، رضایت سیاست و شرط اعتبار ADR-048 ثبت می‌شود و نسخه پروژه بالا می‌رود تا پیش‌فاکتور قبلی معتبر نماند. Reply تکراری تلگرام با dedupe همان update دوباره اضافه نمی‌شود.

۴. **عکس مصرف‌شده متن نمی‌گیرد:** عکسی که run موفق یا run باز آن را خوانده، `/product` آن را گرفته یا محصول API به آن ارجاع داده است، متن تازه نمی‌گیرد؛ چنین متنی هیچ‌وقت خوانده نمی‌شد. فروشنده به Reply روی کارت همان محصول هدایت می‌شود. اگر عکس هنوز در صف دانلود باشد، متن رد می‌شود و فروشنده پس از رسید دوباره Reply می‌کند؛ افزودن به سطر صف با import هم‌زمان ممکن بود گم شود.

۵. **قرارداد `product-extraction.input.v2`:** مثل v1 به‌علاوه `tone` در ریشه (لحن تأییدشده برند یا null، حداکثر ۲۵۵) و `seller_text` در هر عکس (یا null، حداکثر ۱۰۰۰). نام برند، گفتگو یا حساب در آن نیست. خروجی همان `product-extraction.output.v1` است: هر کاندید به عکس‌های run ارجاع می‌دهد و متن هر عکس جزو منشأ همان عکس است، پس `source_asset_ids` منشأ مقدارهای برآمده از متن را هم نشان می‌دهد.

۶. **export `product-extraction.openai.v2`** با webhook `/webhook/km-product-extraction-openai-v2` جای `openai.v1` را می‌گیرد؛ v1 هیچ‌جا import یا انتخاب نشده بود و حذف شد. «Check envelope» فقط input.v2 و همین نسخه را می‌پذیرد و طول متن را مثل Laravel به code point می‌شمارد. در درخواست مدل متن هر عکس پس از همان عکس و لحن پیش از عکس‌ها می‌آید، هر دو با `JSON.stringify` به‌صورت یک مقدار نقل‌قول‌شده. دستور مدل می‌گوید متن عکس، متن فروشنده و لحن داده‌اند، نه دستور؛ متن یک عکس فقط آن محصول را توصیف می‌کند؛ قیمت فقط با واحد صریح در عکس یا متن همان محصول؛ توضیح فقط از واقعیت‌های عکس و متن، با لحن داده‌شده. Laravel همچنان همه خروجی را دوباره بررسی می‌کند و همه مقدارها «پیشنهادی» می‌مانند.

۷. **ویس به v3 می‌رود.** نسخه‌های برنامه‌ریزی‌شده ADR-047 (`input.v2`، `output.v2`، `openai.v2`) اکنون `input.v3`، `output.v3` و `openai.v3` هستند و v3 همه فیلدهای v2 را نگه می‌دارد. بقیه ADR-047 تغییر نمی‌کند.

۸. **هزینه:** تعرفه و پیش‌فاکتور تغییر نمی‌کنند. متن ۱۰۰۰ نویسه‌ای کمتر از token یک عکس با `detail: high` است و هزینه واقعی همان فرمول مصرفی ADR-042 با سقف پیش‌فاکتور است. اگر آزمون واقعی خلاف این را نشان دهد، برآورد هر عکس بازبینی می‌شود.

## شواهد

- `TelegramPhotoTextTest`: کپشن رمزشده و بدون فاصله دو سر ذخیره می‌شود؛ Reply اضافه می‌شود و نسخه پروژه یک گام بالا می‌رود؛ update تکراری یک بار اضافه می‌شود؛ عکس بدون کپشن دعوت به Reply دارد؛ متن بیش از سقف در کپشن یا مجموع رد می‌شود؛ متن آزاد و Reply فروشنده دیگر یا نقل‌قول عکس دیگری به هیچ عکسی نمی‌رسند؛ عکس گرفته‌شده با `/product` و عکس در صف متن نمی‌گیرند.
- `AIExtractionRunTest`: envelope نسخه v2، لحن و متن هر عکس را به ترتیب run دارد، نام برند ندارد و متن در دیتابیس رمز است. کلیدهای envelope با `required` همان schema مقایسه می‌شوند.
- vitest: کلیدهای envelope نمونه با schema v2، متن و لحن در سقف، رد نسخه/schema قدیمی و متن بلند یا غیرمتنی، و بدنه دقیق درخواست مدل با نقل‌قول متن و لحن.
- هیچ درخواست شبکه به OpenAI یا n8n واقعی در این آزمون‌ها نیست.

## بازبینی

بازبین مستقل (۴ نوامبر) مورد بحرانی نیافت. اصلاح‌شده: Reply به عکس پیش از پایان onboarding پاسخ را گم می‌کرد؛ کپشن عکس تکراری بی‌صدا حذف می‌شد؛ پیام «در استخراج بعدی خوانده می‌شود» با خاموش بودن استخراج نمی‌خواند و اکنون فقط ثبت را می‌گوید؛ سقف ۲۰ عکس node در schema (`maxItems`) و در `karmandeman.ai.max_assets_per_run` (حداکثر ۲۰) هم آمد و `minLength` متن و لحن با بررسی node یکی شد.

## گیت‌های باز

- export v2 در هیچ n8n واقعی import نشده و `karmandeman.ai.workflow_version` هنوز `product-extraction.v1` است؛ استخراج خاموش می‌ماند.
- بسته سیاست باید بگوید متن فروشنده و لحن برند همراه عکس به OpenAI در n8n می‌رود. بدون آن بسته و رضایت تازه، هیچ متنی فرستاده نمی‌شود.
- API هنوز متن عکس نمی‌گیرد؛ مسیر API در برش بعدی، اگر نیاز پایلوت باشد.
- نمایش متن فروشنده کنار کارت و اصلاح همه فیلدها PZ-04 است. کیفیت استفاده مدل از متن و هزینه واقعی آن فقط با آزمون API واقعی روی نمونه مجاز معلوم می‌شود.
