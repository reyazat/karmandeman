# ADR-030 — ارسال فایل JSON نسخه نهایی از ربات

تاریخ: ۲۹ اکتبر ۲۰۲۶. وضعیت: تصمیم فنی برش پانزدهم گام ۳، ادامه [ADR-027](ADR-027-bot-batch-finish-and-approval.md)، [ADR-018](ADR-018-batch-finish-input-and-approved-snapshot.md) و [ADR-024](ADR-024-telegram-photo-intake.md). **مجوز intake واقعی در production، انتشار یا پایان گام ۲ نیست.** CSV/PDF/ZIP/کاتالوگ (گام ۶) نیست.

## زمینه

پس از تأیید پروژه در ربات، خروجی JSON فقط از API (`GET /api/v1/projects/{id}/snapshot`) گرفته می‌شد. فروشنده پایلوت با ربات کار می‌کند و API ندارد.

## تصمیم

۱. **دکمه:** پاسخ تأیید پروژه (`ApproveTelegramBatchAction`) دکمه «دریافت فایل JSON» با `project:json:{id}:{number}` دارد. شماره همان snapshot ساخته‌شده یا replayشده است.

۲. **درخواست (webhook):** `RequestTelegramSnapshotAction` پروژه را در Workspace با Policy `view` پیدا می‌کند.
   - پروژه بازگشایی‌شده یا لغوشده: «نسخه نهایی معتبر ندارد». شماره‌ای غیر از آخرین snapshot: «نسخه تازه‌تری ثبت شده». پروژه دیگران: «پروژه یافت نشد». در این حالت‌ها job ساخته نمی‌شود.
   - حداکثر ۵ درخواست در دقیقه برای هر کاربر. دریافت دوباره هزینه و AI ندارد.
   - job `SendTelegramSnapshot` مانند outbox (ADR-008) داخل تراکنش webhook روی صف دیتابیسی `telegram` درج می‌شود (`beforeCommit`). پس پاسخ «در حال آماده‌سازی» و job با هم commit می‌شوند یا هیچ‌کدام.

۳. **payload صف فقط شناسه است:** `user_id`، شناسه عمومی پروژه و شماره snapshot. شناسه چت و داده محصول در صف نیست. پس حذف ردیف‌های حساب کافی است و `forgetChat` outbox نیازی به تطبیق آن ندارد. retention ۲۴ساعته صف `telegram` (ADR-015) این ردیف‌ها را هم پاک می‌کند. job کهنه‌تر از همان مدت بدون ارسال حذف می‌شود.

۴. **worker دوباره همه را بررسی می‌کند:** `SendTelegramSnapshotAction`
   - کاربر یا Workspace ناموجود، یا Workspace غیر `active` (درخواست حذف پس از فشار دکمه): هیچ ارسال یا پیامی (FR-086).
   - همان `ReadProjectSnapshotAction` API با بررسی MAC فهرست و هر نسخه (ADR-018/019). شکست یکپارچگی: پیام «قابل اعتماد نیست»، بدون فایل. پروژه بازگشایی‌شده: «نسخه نهایی معتبر ندارد». snapshot تازه‌تر: «دکمه پیام تأیید تازه را بزن».
   - محتوا همان `ProjectSnapshotResource` است که API زیر کلید `data` می‌دهد، با JSON خوانا و UTF-8. آزمون برابری فایل و API را بررسی می‌کند.
   - نام فایل `karmandeman-{snapshot_id}.json`. توضیح فایل شماره نسخه، نام پروژه و تعداد محصول است.
   - `sendDocument` با multipart. خطای انتقال پرتاب می‌شود تا job دوباره تلاش کند (۳ بار). شناسه چت از هویت Telegram کاربر خوانده می‌شود.

## محدودیت‌ها و کار باز

- **پنجره رقابت حذف:** بررسی وضعیت Workspace پیش از ارسال است، نه زیر قفل. اگر درخواست حذف در چند ثانیه بین بررسی و پاسخ Telegram ثبت شود، فایل همان داده خود فروشنده به چت خود او می‌رسد. نگه‌داشتن قفل Workspace در طول HTTP، webhookهای فروشنده را تا ۳۰ ثانیه معطل می‌کرد. این ریسک باقی‌مانده است و پیش از پایلوت با مالک بازبینی شود.
- ارسال فایل (تا حدود ۳۳ ثانیه در هر تلاش) روی همان worker تکی صف `telegram` اجرا می‌شود و پیام‌های دیگر چت‌ها پشت آن می‌مانند. با حجم پایلوت پذیرفته شد؛ با رشد، صف جدا لازم است.
- Telegram تضمین exactly-once ندارد: timeout مبهم ممکن است فایل را دو بار بفرستد (مانند ADR-008).
- فایلی که به Telegram رفته در کنترل کارمند من نیست و حذف حساب آن را از چت پاک نمی‌کند. متن سیاست باید این را بگوید (بسته سیاست v4).
- عکس‌ها در JSON فقط شناسه asset هستند. ZIP عکس‌ها و سایر خروجی‌ها در گام ۶ است.
- ارسال واقعی به Telegram آزموده نشده است. آزمون‌ها HTTP را fake می‌کنند.
