# ADR-041 — Batch تا تأیید باز است؛ اصلاح پروژه تأییدشده از کارت

تاریخ: ۲ نوامبر ۲۰۲۶. وضعیت: تصمیم مالک. **اصلاح ADR-024، ADR-025، ADR-029 و ADR-040** و بستن تعارض متن محدودیت [ADR-032](ADR-032-n8n-extraction-run-contract.md). وابسته به PRD FR-020…025، §۶ (State Machine و invariantها)، [ADR-019](ADR-019-reopen-cancel-and-approval-integrity.md)، [ADR-028](ADR-028-bot-current-batch-and-reject.md) و [ADR-039](ADR-039-extraction-quote-and-credit-hold.md).

## مسئله

FR-022 می‌گوید «پس از بستن Batch، فایل جدید بدون پرسش وارد پروژه بسته نشود». دو تفسیر در کد بود:
- **API** (ADR-016، ADR-022): ورودی در `collecting_input`، `needs_clarification` و `review_required` پذیرفته می‌شد.
- **ربات** (ADR-024، ADR-025، ADR-040): فقط `collecting_input`. `/done` «بستن» بود و عکس بعدی رد می‌شد.

تا وقتی `/done` را فقط خود فروشنده می‌زد، این تفاوت تحمل‌پذیر بود. با ADR-032 run موفق Batch را خودکار به `review_required` می‌برد. پس محصولی که مدل نمی‌دید از ربات اضافه نمی‌شد، و با رد همه پیشنهادها فقط `/cancel` و `/new` می‌ماند. متن ADR-032 («عکس تازه بفرست یا دستی اضافه کن») هم با رفتار ربات نمی‌خواند. همچنین اصلاح پروژه تأییدشده یک فشار اضافه (دکمه بازگشایی) داشت و عکس از ربات به محصول اضافه نمی‌شد.

## تصمیم مالک (۲ نوامبر ۲۰۲۶)

سادگی برای فروشنده، بدون کار اضافه. ورودی تازه نباید بی‌صدا به پروژه تمام‌شده برود و نباید برای افزودن یا اصلاح محدودیت ایجاد شود.

## تصمیم

۱. **«بستن Batch» در FR-022 یعنی تأیید پروژه، نه `/done`.** Batch تا `product_approved` برای ورودی باز است: `collecting_input`، `needs_clarification`، `extracting` و `review_required`. ربات و API یکسان رفتار می‌کنند.

۲. **مقصد ورودی ربات** (`ResolveTelegramInputProjectAction`، برای عکس، CSV و `/product`):
   - پروژه جاری (ADR-028) اگر باز است، همان.
   - اگر پروژه جاری تأییدشده یا لغوشده است یا پروژه‌ای نیست، پروژه تازه خودکار ساخته و جاری می‌شود. ربات همان لحظه می‌گوید: «پروژه «X» تأیید شده بود؛ پروژه تازه «Y» ساختم و این ورودی در آن ثبت می‌شود». ورودی هرگز بی‌صدا به پروژه تأییدشده نمی‌رود، و هرگز به پروژه قدیمی‌تری که فروشنده انتخاب نکرده برنمی‌گردد (ADR-028).
   - رسید هر عکس نام پروژه را می‌گوید.

۳. **`/done` در بررسی:** اگر عکس تازه‌ای هست که هیچ run موفقی نخوانده و محصولی آن را ندارد، همان پیش‌فاکتور استخراج ADR-039 فقط برای همان عکس‌ها فرستاده می‌شود، همراه کارت محصولات موجود. با تأیید، run تازه از `review_required` شروع می‌شود و محصولات قبلی دست نمی‌خورند. بدون عکس تازه (یا با استخراج خاموش)، `/done` مثل قبل بررسی را نشان می‌دهد. `finish-input` و `extraction-quotes` در API هم `review_required` را با همین شرط می‌پذیرند.

۴. **ورودی وسط استخراج:** عکس و CSV ذخیره و برای `/done` بعدی نگه داشته می‌شوند. run شروع‌شده تغییر نمی‌کند (ADR-032). `/product` در این حالت عکس‌هایی را که run باز می‌خواند برنمی‌دارد، و API وصل‌کردن آن‌ها به محصول را با `409 PRODUCT_IMAGES_BEING_EXTRACTED` رد می‌کند. پس هیچ عکسی دو بار به محصول نمی‌رسد.

۵. **اصلاح پروژه تأییدشده با پاسخ به کارت، بدون فشار اضافه** (اصلاح ADR-029): پاسخ متنی به کارت نسخه جاری محصولی در پروژه `product_approved`، در یک تراکنش همان `ReopenProjectAction` (ADR-019) را اجرا و سپس اصلاح را ثبت می‌کند (`ReopenForCorrectionAction`). اگر اصلاح شکست بخورد، بازگشایی هم برمی‌گردد. پیام می‌گوید پروژه برای اصلاح باز شد و نسخه نهایی قبلی در سابقه محفوظ است. invariant PRD §۶ حفظ می‌شود: snapshot قبلی تا تأیید دوباره خروجی نیست و تأیید دوباره snapshot شماره بعدی می‌سازد. کارت قدیمی (نسخه غیرجاری) هیچ پروژه‌ای را باز نمی‌کند. وضعیت‌های پس از تأیید (پیش‌فاکتور و اعتبار خروجی، گام ۶) خودکار باز نمی‌شوند. دکمه بازگشایی پاسخ‌های قدیمی همچنان کار می‌کند.

۶. **عکس در پاسخ به کارت محصول** (`AttachTelegramPhotoToProductAction`): عکس به Batch همان محصول می‌رود (ADR-023)، نه به پروژه جاری. به نسخه‌ای که کارت نشان داد اضافه و نسخه تازه برای Gate A ساخته می‌شود (حداکثر ۱۰ عکس). پروژه تأییدشده مثل بند ۵ باز می‌شود. بازگشایی، ذخیره و نسخه تازه در یک تراکنش‌اند. صف فقط شناسه محصول و شماره نسخه کارت را نگه می‌دارد (`telegram_media_intakes.target_product_id/target_revision`). کارت قدیمی، محصول Workspace دیگر، محصول ردشده، پروژه لغوشده، محصول با ۱۰ عکس و عکس تکراری همان محصول با پیام روشن رد می‌شوند و چیزی باز یا ذخیره نمی‌کنند. CSV در پاسخ به کارت پذیرفته نمی‌شود.

۷. **بازبینی مستقل:** P1 نیافت. یافته‌ها، همه با آزمون اصلاح شدند:
   - **(P2)** عکس در پاسخ به کارت با همان بایت‌های عکس محصول دیگر یا عکسی که run می‌خواند، آن را از صاحبش می‌گرفت (dedupe محتوا، سپس claim). اکنون رد می‌شود (`PHOTO_USED_ELSEWHERE`). اصلاح API (`PATCH /products/{id}/draft`) هم عکس run باز را نمی‌پذیرد (`PRODUCT_IMAGES_BEING_EXTRACTED`).
   - **(P2)** آلبوم چندعکسی پس از تأیید، که Telegram آن را با updateهای هم‌زمان می‌فرستد، می‌توانست چند پروژه تازه بسازد. اکنون پروژه مقصد زیر قفل Workspace خوانده می‌شود.
   - **(P2)** شکست run شروع‌شده از بررسی، پروژه‌ای را که قابل تأیید بود به `collecting_input` می‌برد. اکنون پروژه دارای محصول به بررسی برمی‌گردد.
   - **(P3)** پیش‌فاکتور استخراج با هر فشار Gate A کهنه می‌شد. اکنون اعتبار آن فقط به همان عکس‌ها بسته است، نه نسخه پروژه (اصلاح ADR-039 بند ۴). عکس تازه یا مصرف‌شده همچنان آن را باطل می‌کند.
   - **(P3)** رد محصول وسط استخراج ممکن نبود. اکنون ممکن است.
   - **(P3)** خطاهای پیش‌بینی‌نشده مسیر عکس کارت بی‌پاسخ می‌ماندند. اکنون پیام می‌گیرند.
   - **(P3)** تکرار job پس از commit پیام «کارت قدیمی» می‌داد. اکنون هر قدم با کلیدش replay می‌شود.
   - **(P3)** عکسی که درست پیش از تأیید صف شده بود رد می‌شد. اکنون به پروژه تازه می‌رود.

## گزینه‌های ردشده

- **دکمه «افزودن ورودی»:** یک اقدام اضافه برای فروشنده. مالک رد کرد.
- **پذیرش در پروژه تأییدشده با پرسش:** پروژه‌ای که خروجی‌اش ساخته شده با یک عکس بی‌صدا تغییر می‌کرد. پروژه تازه پیش‌فرض امن‌تری است و اصلاح عمدی با پاسخ به کارت انجام می‌شود.
- **انتقال فایل رمزشده بین پروژه‌ها:** عکس در پاسخ به کارت همان نیاز را بدون جابه‌جایی فایل برآورده می‌کند.

## شواهد

- `TelegramOpenBatchTest` (۸ مورد): عکس محصول دیگر یا عکس run از کارت و PATCH رد، رد محصول وسط استخراج، شکست run از بررسی، پیش‌فاکتور پس از Gate A؛ عکس در پاسخ به کارت پروژه تأییدشده (بازگشایی، نسخه تازه با عکس، claim، snapshot ۴۰۹)؛ کارت بیگانه، کهنه و پر بدون بازگشایی و ذخیره؛ عکس تکراری؛ `/done` در بررسی فقط عکس تازه را قیمت می‌دهد و کارت‌ها را نشان می‌دهد؛ ورودی وسط استخراج و حفاظت از عکس‌های run در ربات و API؛ پروژه تازه پس از تأیید.
- آزمون‌های به‌روزشده: `TelegramProductEditTest` (اصلاح پروژه تأییدشده در یک قدم تا snapshot شماره ۲، دکمه قدیمی کهنه یا بیگانه بی‌اثر)، `TelegramPhotoIntakeTest` (پروژه تازه بدون پروژه باز یا پس از تأیید، پذیرش در بررسی)، `TelegramProductCommandTest`، `TelegramProjectCancelTest`، `TelegramProjectSelectionTest`، `TelegramBatchApprovalTest`، `TelegramBotRefusalRepliesTest` و `AIExtractionRunTest`.
- PostgreSQL موقت با OpenBao 2.4.1: **۳۶۶ تست / ۵۰۶۶ assertion** در دو اجرای پیاپی. SQLite **۳۳۹ پاس / ۲۷ skip**. Pint و PHPStan بدون خطا. rollback و اجرای دوباره migration `add_telegram_intake_card_target` روی PostgreSQL موقت، دو بار، موفق.

## محدودیت‌ها

- اصلاح متنی از ربات هنوز فقط نام و قیمت است. اصلاح کد، توضیحات و ویژگی با برچسب در پاسخ به کارت برش بعدی است.
- اگر نوشتن نسخه تازه پس از ذخیره فایل شکست بخورد، شیء رمزشده بدون ردیف در storage همان Workspace می‌ماند تا حذف حساب. احتمالش کم است، چون کارت کهنه پیش از ذخیره رد می‌شود.
- ربات زنده آزموده نشده است. اینکه Telegram دکمه‌های کارت را در `reply_to_message` عکس بفرستد، مثل ADR-029 فقط با payload مستند Bot API شبیه‌سازی شده است.
