# ADR-024 — دریافت عکس محصول از ربات تلگرام

تاریخ: ۲۹ اکتبر ۲۰۲۶. وضعیت: تصمیم فنی برش نهم گام ۳، ادامه [ADR-022](ADR-022-private-encrypted-asset-storage.md) و [ADR-023](ADR-023-product-photos-from-batch-assets.md) (PRD FR-025، FR-030، [DEVELOPMENT_PLAN](../DEVELOPMENT_PLAN.md) گام ۳: «یک محصول ساده از متن/عکس»). **مجوز intake واقعی در production، انتشار یا پایان گام ۲ نیست.**

## زمینه

ADR-022 بارگذاری عکس را فقط از API ساخت. کانال اصلی پایلوت ربات تلگرام است و PRD می‌خواهد فایل «از تلگرام به مخزن امن مستقل منتقل شود» تا حذف چت یا منقضی‌شدن لینک تلگرام آن را از بین نبرد. تلگرام و n8n adapter نامطمئن‌اند (AGENTS.md).

## تصمیم

۱. **دریافت در webhook:** پیام خصوصی با `photo` یا `document` (فقط `image/jpeg`، `image/png`، `image/webp`) به `QueueTelegramPhotoAction` می‌رسد. caption نادیده گرفته می‌شود و هرگز دستور حساب نمی‌شود.
   - از عکس، بزرگ‌ترین اندازه انتخاب می‌شود. document کیفیت اصلی را دارد.
   - شرط‌ها به ترتیب: حساب در حال حذف نیست، onboarding کامل است، نوع مجاز است، حجم اعلام‌شده بیش از سقف ADR-022 (۱۰ مگابایت) نیست، رضایت سیاست ثبت شده، پروژه‌ای در `collecting_input` هست، و Policy `update` روی آن.
   - **سقف سرعت:** همان بودجه بارگذاری API برای هر کاربر (`KM_ASSET_UPLOADS_PER_MINUTE`، پیش‌فرض ۲۰ در دقیقه). بیشتر از آن صف نمی‌شود و کاربر پیام «صبر کن» می‌گیرد.
   - **پروژه مقصد:** جدیدترین پروژه Workspace در `collecting_input`. پاسخ `/new` این را به کاربر می‌گوید. بدون پروژه باز، پاسخ «اول با /new یک پروژه بساز» است.
   - در webhook چیزی دانلود نمی‌شود. فقط یک ردیف `telegram_media_intakes` ساخته می‌شود: شناسه‌ها، `file_id` رمزشده با کلید Workspace (`file_ref`)، حجم اعلام‌شده و کلید پیام. کلید پیام digest کلیددار chat و `message_id` است (`TelegramSubjectKey::message`) و یکتاست، پس پیام تکراری دوباره صف نمی‌شود.
   - job `ImportTelegramPhoto` پس از commit صف می‌شود و **فقط شناسه ردیف** را حمل می‌کند. payload صف و `failed_jobs` نه chat id دارند، نه file id و نه بایت فایل. پس حذف ردیف برای erasure کافی است.

۲. **دانلود در job:** `ImportTelegramPhotoAction`:
   - اگر ردیف نیست (purge یا retention)، کاری نمی‌کند. اگر Workspace دیگر `active` نیست، چیزی دانلود نمی‌شود و ردیف بی‌پاسخ پاک می‌شود.
   - `getFile` و دانلود سمت سرور با token فقط در URL. پیام exceptionها token و URL ندارند.
   - پروژه باید هنوز در `collecting_input` باشد. عکسی که پیش از «پایان ورودی» صف شده، پس از آن پذیرفته نمی‌شود و کاربر پیام رد می‌گیرد.
   - سقف حجم چهار بار بررسی می‌شود: حجم اعلام‌شده در پیام، حجم `getFile`، `Content-Length` پاسخ دانلود (در هر عمق از زنجیره exception کلاینت HTTP) و طول واقعی بدنه. بدون `Content-Length` بدنه پیش از رد کامل دریافت می‌شود، که سقف ۲۰ مگابایت `getFile` آن را محدود می‌کند.
   - بایت‌ها از همان `AttachProjectAssetAction` می‌گذرند: بررسی نوع از بایت‌ها، رمزنگاری، Policy، رضایت، وضعیت پروژه، قفل Workspace و حذف تکرار. `source` برابر `telegram` و `source_message_key` برابر کلید پیام است (FR-030).
   - کلید idempotency از کلید پیام ساخته می‌شود، پس retry پس از ذخیره همان asset را برمی‌گرداند.
   - پاسخ از outbox: «عکس به پروژه … اضافه شد»، «قبلاً ثبت شده بود» یا دلیل رد. حذف ردیف و صف‌کردن پاسخ در یک تراکنش‌اند، پس از قفل ردیف Workspace به همان ترتیب purge. اگر حذف حساب در این فاصله شروع شده باشد، پاسخی صف نمی‌شود.
   - خطای شبکه یا تلگرام retry می‌شود (۳ بار). پس از آخرین شکست، ردیف پاک و «دریافت ناموفق بود؛ دوباره بفرست» فرستاده می‌شود.

۳. **حذف و نگهداری:**
   - `telegram_media_intakes` در فهرست purge حذف حساب است.
   - retention ردیف گیرکرده را پس از `KM_RETENTION_MEDIA_INTAKE_HOURS` (پیش‌فرض ۲۴ ساعت) پاک می‌کند.
   - asset ذخیره‌شده مانند ADR-022 تا حذف حساب می‌ماند.

۴. **اعتبارسنجی webhook:** FormRequest فقط فیلدهای لازم `photo` (حداکثر ۲۰ اندازه) و `document` را می‌پذیرد و بقیه را دور می‌ریزد.

## محدودیت‌ها و کار باز

- **متن محصول از تلگرام ساخته نشده است.** پیام متنی همچنان به onboarding برند می‌رود. ساخت پیش‌نویس محصول از عکس و متن تلگرام برش بعدی است. تا آن زمان محصول با API ساخته می‌شود و عکس‌های تلگرام را با `image_asset_ids` وصل می‌کند.
- **انتخاب پروژه ضمنی است.** کاربری که چند پروژه باز دارد عکس را در جدیدترین می‌بیند. انتخاب صریح پروژه (دکمه یا دستور) ساخته نشده است.
- **dispatch پس از commit:** اگر push به Redis پس از commit شکست بخورد، webhook ‏503 می‌دهد و تلگرام دوباره می‌فرستد، ولی update تکراری حساب می‌شود. ردیف بی‌job تا ۲۴ ساعت می‌ماند و retention آن را پاک می‌کند. کاربر پاسخی نمی‌گیرد. outbox تراکنشی برای این job ساخته نشده است.
- **media فورواردشده** از دیگران مانند عکس خود فروشنده پذیرفته می‌شود، چون `forward_origin` بررسی نمی‌شود. مسئولیت حق استفاده با فروشنده است (بسته سیاست).
- اگر asset ذخیره شود ولی پاک‌کردن ردیف شکست بخورد و retry دانلود هم شکست بخورد، کاربر «ناموفق» می‌شنود با اینکه عکس ذخیره شده است. ارسال دوباره همان asset را برمی‌گرداند.
- album (`media_group_id`) جداگانه، هر عکس به‌عنوان یک پیام، دریافت می‌شود.
- سقف Bot API برای `getFile` بیست مگابایت است. سقف ما ده مگابایت است. فایل بزرگ‌تر با پیام رد می‌شود.
- دسته نگهداری فایل‌ها و ردیف‌های intake در بسته سیاست تعریف نشده است. تغییر بسته سیاست، digest رضایت را عوض می‌کند و تصمیم مالک محصول است.
- ربات زنده، Bot API واقعی و صف Redis production آزموده نشده‌اند. آزمون‌ها HTTP جعلی و صف sync دارند.
- endpointها و مسیر ربات تا تصویب سیاست در production با نبود رضایت بسته می‌مانند.
