# ADR-029 — اصلاح محصول از ربات و بازگشایی اجباری پروژه تأییدشده

تاریخ: ۲۹ اکتبر ۲۰۲۶. وضعیت: تصمیم مالک محصول و تصمیم فنی برش چهاردهم گام ۳، ادامه [ADR-028](ADR-028-bot-current-batch-and-reject.md)، [ADR-019](ADR-019-reopen-cancel-and-approval-integrity.md) و [ADR-018](ADR-018-batch-finish-input-and-approved-snapshot.md) (PRD §۶، FR-033). **مجوز intake واقعی در production، انتشار یا پایان گام ۲ نیست.**

## زمینه

- اصلاح محصول فقط با API ممکن بود. در ربات راه اصلاح «رد و ارسال دوباره» بود (ADR-028).
- ADR-019 یک تعارض با PRD §۶ را باز گذاشته بود: طبق ADR-018 (تصمیم ۳) اصلاح و Gate A محصول در پروژه `product_approved` بدون reopen مجاز بود. snapshot قدیمی خروجی می‌ماند، ولی نسخه تأییدشده تازه محصول عدد دیگری داشت. PRD می‌گوید «Approval کاربر نسبت به version قبلی پس از تغییر رکورد معتبر نیست».
- مالک محصول در ۲۹ اکتبر ۲۰۲۶ گزینه «reopen اجباری» را انتخاب کرد: در پروژه تأییدشده، اصلاح فقط پس از بازگشایی پروژه انجام می‌شود.

## تصمیم

۱. **بازگشایی اجباری (همه کانال‌ها):** `ReviseProductDraftAction` و `ArchiveProductAction` برای محصولی که پروژه آن در وضعیت دارای snapshot است (`ProjectState::hasApprovedSnapshot()`، یعنی `product_approved` و پس از آن) خطای `PROJECT_REOPEN_REQUIRED` می‌دهند. پاسخ API `409` است.
   - رد (archive) هم مشمول است: حذف محصول از Batch تأییدشده به اندازه اصلاح آن را تغییر می‌دهد. پیش از این، رد با API در هر وضعیتی مجاز بود (ADR-028، محدودیت ۲).
   - رد در پروژه لغوشده مجاز می‌ماند تا SKU آزاد شود (ADR-019).
   - Gate A تغییری نمی‌کند: در پروژه تأییدشده نسخه جاری هر محصول فعال همان نسخه تأییدشده است، پس Gate A چیز تازه‌ای تأیید نمی‌کند.
   - رفتار ADR-018 (تصمیم ۳) کنار گذاشته شد. تعارض ثبت‌شده در ADR-019 بسته شد.

۲. **اصلاح با پاسخ به کارت:** فروشنده به کارت محصول (`TelegramProductCard`) پاسخ (Reply) می‌دهد. خط اول نام، خط دوم (اختیاری) قیمت با واحد است. قالب و parser همان `/product` است (`TelegramProductText`).
   - کارت هدف از دکمه‌های inline پیام پاسخ‌داده‌شده خوانده می‌شود (`product:approve|reject:{id}:{rev}`). پس اصلاح فقط روی همان نسخه‌ای است که کارت نشان داد. اگر محصول پس از کارت تغییر کرده باشد، `PRODUCT_REVISION_CONFLICT`.
   - پیام پاسخ‌داده‌شده باید از خود ربات باشد: `from.is_bot` و `from.id` برابر شناسه ربات (بخش اول token). پیام دیگری کارت حساب نمی‌شود و متن عادی است. فرمان (`/...`) حتی به‌صورت پاسخ فرمان است.
   - جستجوی محصول فقط در Workspace کاربر است و Policy `update` لازم است. کارت فوروارد‌شده به فروشنده دیگر به «محصول یافت نشد» می‌رسد.
   - پیش از بازسازی، MAC محتوای نسخه نشان‌داده‌شده بررسی می‌شود. payload جابه‌جاشده در DB با اصلاح از ربات MAC تازه نمی‌گیرد و پاسخ «قابل اعتماد نیست» است.
   - بدون خط دوم، قیمت قبلی می‌ماند. سایر فیلدها (SKU، توضیح، ویژگی‌ها، دسته، عکس‌ها) دست نمی‌خورند: پیش‌نویس از payload نسخه نشان‌داده‌شده با `ProductDraftNormalizer::draftFrom()` بازسازی می‌شود. متن خام از `originals` برمی‌گردد، پس نرمال‌سازی دوباره همان payload را می‌دهد (آزمون round trip).
   - کلید idempotency از `message_id` است. ارسال دوباره همان پیام با `update_id` تازه یک نسخه می‌سازد. نرخ همان محدودیت `/product` است.
   - پاسخ موفق کارت نسخه تازه با دکمه تأیید و رد آن نسخه است. هر کارت متن «برای اصلاح، به همین پیام پاسخ بده» دارد و `/help` آن را می‌گوید.

۳. **بازگشایی از ربات:** اصلاح در پروژه تأییدشده با پیام توضیح و دکمه «بازگشایی پروژه برای اصلاح» (`project:reopen:{id}:{version}`) پاسخ داده می‌شود.
   - دکمه فقط برای `product_approved` می‌آید. وضعیت‌های بعدی (Quote/اعتبار) پیام «از مرحله تأیید گذشته» می‌گیرند، نه دکمه‌ای که همیشه رد می‌شود.
   - دکمه همان `ReopenProjectAction` را با نسخه نشان‌داده‌شده اجرا می‌کند. نسخه کهنه `PROJECT_VERSION_CONFLICT`. پروژه Workspace دیگر «پروژه یافت نشد».
   - پس از بازگشایی، پروژه جاری ربات می‌شود (ADR-028) و کارت همه محصولات فعال (حداکثر ۱۰) دوباره فرستاده می‌شود تا فروشنده به آن‌ها پاسخ دهد.
   - تا تأیید دوباره، snapshot قبلی خروجی نیست (`409 PROJECT_NOT_APPROVED`، ADR-019). `/done` و دکمه تأیید پروژه snapshot شماره بعدی را می‌سازند.

۴. **اعتبارسنجی webhook:** فقط `reply_to_message.from.id`، `from.is_bot` و `callback_data` دکمه‌های آن نگه داشته می‌شوند. متن کارت پاسخ‌داده‌شده خوانده یا ذخیره نمی‌شود. برای این فیلدها قاعده اندازه یا نوع نیست: پاسخ به هر پیام دیگری (مثلاً پیام inline با بیش از ۲۰ ردیف دکمه) نباید `422` بگیرد، چون Telegram آن را بی‌پایان تکرار می‌کند. سرویس شکل را بررسی می‌کند و هرچه کارت نباشد متن عادی است (یافته P2 بازبین، بازتولیدشده).

## محدودیت‌ها و کار باز

- فقط نام و قیمت از ربات اصلاح می‌شوند. اصلاح عکس، SKU، توضیح، ویژگی و دسته از ربات ساخته نشده است.
- اصلاح بدون تغییر هم نسخه تازه می‌سازد.
- اگر Telegram دکمه‌های کارت را در `reply_to_message` نفرستد، پاسخ متن عادی حساب می‌شود. این رفتار در ربات واقعی آزموده نشده است؛ آزمون‌ها payload مستند Bot API را شبیه‌سازی می‌کنند.
- لغو پروژه از ربات ساخته نشده است.
- بازگشایی وضعیت‌های پس از `product_approved` (Quote/اعتبار) به گام ۵ موکول است.
