# ADR-044 — هماهنگی ربات و API پس از Batch باز تا تأیید

تاریخ: ۲ نوامبر ۲۰۲۶. وضعیت: پیاده‌سازی شد. **اصلاح ADR-025 (محدودیت عکس)، ADR-028 (تعریف پروژه باز و دکمه رد) و تکمیل ADR-041.** وابسته به PRD FR-022، FR-041 و FR-080، [ADR-019](ADR-019-reopen-cancel-and-approval-integrity.md)، [ADR-023](ADR-023-product-photos-from-batch-assets.md)، [ADR-039](ADR-039-extraction-quote-and-credit-hold.md) و [ADR-043](ADR-043-credit-usage-and-ledger-reconciliation.md).

## مسئله

ممیزی هماهنگی (۲ نوامبر) همه مسیرهای API را با فرمان‌ها و دکمه‌های ربات مقایسه کرد. قاعده ADR-041 («Batch تا تأیید برای ورودی باز است») در مسیر ورودی اعمال شده بود، ولی چند بخش دیگر هنوز قاعده قبلی را فرض می‌کردند:

- **(P2)** عکسی که محصول API آن را داشت علامت ربات نمی‌گرفت. پس `/product` بعدی ربات همان عکس را به محصول تازه وصل می‌کرد. ADR-025 این را محدودیت ثبت کرده بود. با ADR-041 هر دو کانال در بررسی ورودی می‌گیرند و احتمالش بیشتر شده بود.
- **(P2)** پاسخ متنی یا عکس به کارت محصول پروژه تأییدشده را خودکار باز می‌کرد، ولی دکمه «رد» همان کارت فقط می‌گفت «پروژه دیگر در حال بررسی نیست».
- **(P2)** `/projects`، دکمه انتخاب و fallback پروژه جاری فقط `collecting_input` و `review_required` را باز می‌دانستند. پروژه در حال استخراج انتخاب نمی‌شد، پس فروشنده نمی‌توانست به آن برگردد تا عکس اضافه کند. تعریف «باز» در شش جای کد تکرار شده بود.
- **(P3)** پیام‌های «ورودی پروژه بسته است» در `/done` و انتخاب پروژه، پیشنهاد `/new` برای پروژه تأییدشده، و `/help` بدون CSV و عکس در پاسخ به کارت.
- **(P3)** FR-080 («هر پروژه نام، تاریخ، وضعیت، فایل‌ها، مصرف داشته باشد») در هیچ کانالی کامل نبود. ربات وضعیت را با نام انگلیسی enum نشان می‌داد.
- **(P3)** ADR-041 تفاوت عمدی دو کانال در پروژه تأییدشده را ننوشته بود.

## تصمیم

۱. **یک تعریف برای «باز برای ورودی»:** `ProjectState::OPEN_FOR_INPUT` و `isOpenForInput()` شامل `collecting_input`، `needs_clarification`، `extracting` و `review_required`. همه این‌ها از همین تعریف استفاده می‌کنند: عکس، CSV و محصول API، مقصد ورودی ربات، `/projects`، دکمه انتخاب، fallback پروژه جاری (ADR-028) و رد با نسخه مشخص. این تصمیم ADR-028 بند ۱ و ۲ را اصلاح می‌کند. پیام انتخاب پروژه در استخراج می‌گوید ورودی تازه برای `/done` بعدی می‌ماند.

۲. **عکسی که محصولی دارد دوباره داده نمی‌شود:** `/product` عکس‌هایی را برنمی‌دارد که نسخه جاری یک محصول زنده همان Batch به آن‌ها ارجاع می‌دهد، از هر کانالی که باشد (`ProductRepository::citedImageIds`). این همان قاعده‌ای است که پیش‌فاکتور استخراج (ADR-041 بند ۳) و عکس در پاسخ به کارت از قبل داشتند. حالا هر سه از یک تابع استفاده می‌کنند، با یک query برای کل Batch. migration لازم نیست. ستون `claimed_by_product_id` همچنان فقط ثبت می‌کند ربات چه چیزی را واگذار کرده است (ADR-025). عکس محصول ردشده دوباره آزاد می‌شود، چون محصول ردشده در فهرست محصولات زنده نیست. این تصمیم محدودیت اول ADR-025 را می‌بندد.

۳. **رد از کارت در پروژه تأییدشده، بدون فشار اضافه:** دکمه «رد» روی کارت نسخه جاری مثل اصلاح عمل می‌کند (ADR-041 بند ۵). در یک تراکنش، اول `ReopenForCorrectionAction` و بعد `ArchiveProductAction` اجرا می‌شود. اگر رد شکست بخورد، بازگشایی هم برمی‌گردد. پاسخ می‌گوید پروژه برای اصلاح باز شد و جاری است. snapshot قبلی در سابقه می‌ماند و تا تأیید دوباره خروجی نیست (PRD §۶).
   - کارت قدیمی (نسخه غیرجاری) چیزی باز نمی‌کند. پاسخ آن «تغییر کرده است» است و پروژه تأییدشده و `version` آن دست نمی‌خورند.
   - پروژه پس از تأیید (پیش‌فاکتور یا اعتبار خروجی، گام ۶) باز نمی‌شود و رد نمی‌شود.
   - تصمیم بازگشایی زیر قفل Workspace و روی وضعیت تازه محصول گرفته می‌شود. محصولی که از قبل رد شده، حتی با نسخه‌ای برابر کارت، پاسخ «قبلاً رد شده است» می‌گیرد و چیزی باز نمی‌کند.
   - ربات Gate را از قبل بررسی نمی‌کند. اجازه را خود رد و بازگشایی پس از قفل بررسی می‌کنند، تا درخواست حذف حساب همان پاسخ حذف را بگیرد (FR-086). جست‌وجوی محصول به Workspace کاربر محدود است.

۴. **پیام‌ها:** خلاصه بررسی `/done` «پروژه در بررسی است» می‌گوید و اعلام می‌کند تا تأیید پروژه ورودی تازه هم پذیرفته می‌شود. `/done` روی پروژه تأییدشده یا لغوشده می‌گوید ورودی بعدی خودش پروژه تازه می‌سازد، و برای پروژه تأییدشده راه اصلاح از کارت را می‌گوید. پیام شروع استخراج دیگر «ورودی بسته شد» نمی‌گوید. `/help` فایل CSV، ساخت خودکار پروژه تازه، بازشدن خودکار با اصلاح و عکس در پاسخ به کارت را دارد.

۵. **FR-080:**
   - **ربات:** `/projects` (`TelegramProjectList`) برای ۵ پروژه آخر این‌ها را نشان می‌دهد: نام، وضعیت فارسی، تاریخ ساخت (`Y-m-d`، مثل نام پیش‌فرض پروژه)، تعداد عکس، تعداد فایل CSV، تعداد محصول زنده و اعتبار مصرف‌شده.
   - **API:** هر ردیف `GET /api/v1/projects` شیء `activity` دارد: `photos`، `tables`، `products` و `credits_used`. پاسخ‌های دیگر پروژه این شیء را ندارند.
   - **روش شمارش:** `ProjectRepository::activityFor` برای هر صفحه چهار query گروهی اجرا می‌کند. همه به `workspace_id` همان Workspace محدودند. مصرف برابر منفی جمع ردیف‌های `capture` ledger است، فقط وقتی کیف پول و run هر دو از همان Workspace باشند و run به همان پروژه تعلق داشته باشد (ADR-042، ADR-043).

۶. **تفاوت عمدی دو کانال در پروژه تأییدشده:**
   - **API** همچنان بازگشایی صریح می‌خواهد (`POST /projects/{id}/reopen`). عکس و CSV در پروژه تأییدشده `409 PROJECT_NOT_ACCEPTING_INPUT` می‌گیرند، محصول تازه `409 PROJECT_NOT_ACCEPTING_PRODUCTS`، و اصلاح یا رد محصول `409 PROJECT_REOPEN_REQUIRED`.
   - **ربات** پروژه را از کارت خودکار باز می‌کند، یا برای ورودی تازه پروژه تازه می‌سازد.
   - **دلیل:** در API فراخواننده پروژه را با شناسه صریح نام می‌برد. بازگشایی بی‌صدا snapshot تأییدشده را بدون اقدام عمدی یک integration از خروجی خارج می‌کرد. در ربات پاسخ به کارت یک محصول مشخص، خودش همان اقدام عمدی است.

## بازبینی مستقل

- **(P1، اصلاح شد)** کارت قدیمی محصولی که پیش از تأیید رد شده بود، پروژه تأییدشده را دوباره باز می‌کرد. رد محصول `current_revision` را عوض نمی‌کند، پس نسخه کارت هنوز «جاری» بود، و رد دوم بی‌اثر ولی موفق بود و بازگشایی برنمی‌گشت. اکنون محصول ردشده پیش از بازگشایی رد می‌شود. آزمون تازه بدون اصلاح شکست می‌خورد.
- **(P3، اصلاح شد)** تصمیم «پس از تأیید» پیش از قفل گرفته می‌شد، پس درخواست حذف حساب پاسخ نادرست می‌گرفت. اکنون همه تصمیم‌ها زیر قفل‌اند.
- **(P3، اصلاح شد)** پیام `PROJECT_STATE_CONFLICT` همیشه «لغو شده» می‌گفت. اکنون متن خنثی است.
- **(P3، اصلاح شد)** `citedImageIds` برای هر محصول یک query می‌زد. اکنون یک query با join است.
- **(P3، ثبت‌شده)** `needs_clarification` هنوز هیچ مسیری ندارد که پروژه را به آن ببرد. پیام‌های آن آماده‌اند ولی اجرا نمی‌شوند.

## گزینه‌های ردشده

- **علامت‌زدن عکس در API (`claimed_by_product_id`):** نوشتن روی هر create و revise، و مسئله عکسی که بعداً از محصول جدا می‌شود. خواندن از نسخه جاری محصولات همان قاعده پیش‌فاکتور است و به داده تازه نیاز ندارد.
- **بازگشایی خودکار در API:** بند ۶.
- **دکمه جدا «بازگشایی و رد»:** یک فشار اضافه. مالک در ADR-041 همین را رد کرد.

## شواهد

- آزمون‌های تازه در `TelegramOpenBatchTest`:
  - رد در پروژه تأییدشده، بازگشایی و رد را در یک قدم انجام می‌دهد. snapshot قبلی می‌ماند و snapshot جاری ۴۰۹ است. کارت قدیمی، محصولی که پیش از تأیید رد شده، و پروژه پس از تأیید چیزی باز نمی‌کنند.
  - `/product` عکسی را که محصول API دارد برنمی‌دارد.
  - پروژه در حال استخراج در `/projects` فهرست و انتخاب می‌شود و عکس می‌گیرد.
  - فهرست پروژه در API و ربات شمارش و مصرف درست را نشان می‌دهد، و پروژه Workspace دیگر در آن نمی‌آید.
- آزمون‌های به‌روزشده: `TelegramProjectSelectionTest` (وضعیت فارسی و تاریخ، پیام پروژه بسته، کارت کهنه پس از رد با API) و `TelegramBatchApprovalTest` (متن بررسی).
- PostgreSQL موقت با OpenBao 2.4.1: **۳۹۱ تست / ۵۴۱۳ assertion** در دو اجرای پیاپی، بدون skip. SQLite **۳۶۴ پاس / ۲۷ skip**. Pint و PHPStan بدون خطا.

## محدودیت‌ها

- `credits_used` فقط کسرها را جمع می‌کند. وقتی refund و adjustment اپراتور ساخته شوند (گام ۵، باز)، این عدد باید آن‌ها را هم کم کند.
- تاریخ فهرست میلادی و به منطقه زمانی سرور است. تقویم شمسی تصمیم جداگانه نمایش است.
- اصلاح متنی از ربات هنوز فقط نام و قیمت است (ADR-041).
