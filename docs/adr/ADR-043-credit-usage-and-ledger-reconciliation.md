# ADR-043 — شفافیت مصرف اعتبار، تطبیق دوره‌ای ledger و نگهداری پیش‌فاکتور

تاریخ: ۲ نوامبر ۲۰۲۶. وضعیت: پیاده‌سازی شد. بدون تغییر تصمیم قبلی. وابسته به PRD FR-073، FR-084، E08 و E10، [ADR-015](ADR-015-retention-enforcement-and-identity-minimisation.md)، [ADR-039](ADR-039-extraction-quote-and-credit-hold.md) و [ADR-042](ADR-042-usage-based-output-charge.md).

## مسئله

گام ۵ پس از ADR-042 سه کار بی‌نیاز از تصمیم مالک داشت:

- **FR-073:** «هر کسر به Project/Output/Run و علت متصل باشد». ledger این پیوند را در `related_type`/`related_id` داشت، ولی API فقط نوع، مبلغ و علت را برمی‌گرداند. `/balance` ربات فقط موجودی را می‌گفت.
- **reconciliation دوره‌ای:** invariantهای ADR-039 و ADR-042 فقط در آزمون بررسی می‌شدند. اگر در production یک cache از جمع ledger جدا شود یا رزروی تسویه نشود، کسی خبردار نمی‌شد.
- **نگهداری پیش‌فاکتور پذیرفته‌نشده:** هر `/done` یک پیش‌فاکتور می‌سازد. پیش‌فاکتور پذیرفته‌نشده پس از ۱۵ دقیقه بی‌مصرف است ولی تا حذف حساب می‌ماند.

## تصمیم

۱. **API کیف پول.** هر ردیف `GET /api/v1/wallet/ledger` اکنون این فیلدها را هم دارد:
   - `output_class`: کلاس خروجی ADR-042 (فعلاً فقط `file_to_text`).
   - `run_id` و `project_id`: شناسه عمومی run و پروژه.

   برای هدیه و هر ردیف بی‌run هر سه `null` هستند. run فقط در Workspace همان کیف پول جست‌وجو می‌شود. پس ردیفی که به run Workspace دیگری اشاره کند هیچ شناسه‌ای از آن نشان نمی‌دهد. usage خام، نرخ و تعرفه در API نمی‌آیند (ADR-042: یک عدد).

۲. **`/balance` ربات.** پس از موجودی و رزرو، حداکثر ۵ کسر آخر می‌آید، هر کدام یک خط: «• 3 اعتبار: استخراج محصول از 2 عکس، پروژه «X»». آزادسازی و رزرو کسر نیستند و نمی‌آیند.

۳. **`credits:reconcile`، روزانه ساعت ۰۳:۴۰.** فقط گزارش می‌دهد و هیچ چیزی را اصلاح نمی‌کند، چون فقط adjustment اپراتور با دلیل (E08) می‌تواند اعتبار را بیرون از use case جابه‌جا کند. بررسی‌ها:

   | بررسی | یعنی |
   |---|---|
   | `balance_cache_drift` / `reserved_cache_drift` | cache کیف پول با جمع `amount` / `held_amount` ledger برابر نیست |
   | `hold_unsettled` | run بسته شده ولی رزرو آن تسویه نشده |
   | `hold_without_run` | رزرو تسویه‌نشده‌ای که run آن وجود ندارد |
   | `settled_open_run` | رزرو تسویه شده ولی run هنوز باز است |
   | `settlement_hold_mismatch` | ردیف تسویه کل رزرو را نمی‌بندد |
   | `capture_outside_hold` | کسر کمتر از ۱ یا بیشتر از رزرو |
   | `release_moved_balance` | آزادسازی موجودی را تغییر داده |
   | `settlement_without_hold` | کسر یا آزادسازی بدون رزرو پشت کلید آن |
   | `settlement_of_another_target` | ردیف تسویه به run دیگری جز run رزرو اشاره دارد |
   | `settlement_disagrees_with_run` | run موفق آزاد شده یا run ناموفق کسر داده |
   | `run_of_another_workspace` | رزرو به run Workspace دیگری اشاره دارد |

   هر یافته با `credit.reconcile_mismatch` و فقط شناسه داخلی کیف پول و شناسه عمومی ردیف لاگ می‌شود، بدون محتوای فروشنده. با هر یافته خروجی فرمان شکست است تا scheduler و پایش آن را ببینند. سه query جدا اجرا می‌شوند: drift کش‌ها، رزروها با تسویه و run، و تسویه بی‌رزرو. هر query در یک دستور SQL همه داده لازمش را می‌خواند. پس commit در حال اجرا یافته کاذب نمی‌سازد، چون بستن run و تسویه در یک تراکنش‌اند (ADR-039).

۴. **نگهداری پیش‌فاکتور.** `privacy:prune-retention` پیش‌فاکتوری را که ۱۶۸ ساعت از ساختش گذشته و پذیرفته نشده حذف می‌کند (`KM_RETENTION_CREDIT_QUOTE_HOURS`). مقدار کمتر از عمر پیش‌فاکتور به‌اضافه یک ساعت اثر ندارد، تا پیش‌فاکتوری که در حال پذیرش است پاک نشود. پیش‌فاکتور پذیرفته‌شده با run و ردیف ledger تا حذف حساب می‌ماند، چون مبنای حسابرسی کسر است (تعرفه ADR-042). فشار دکمه یک پیش‌فاکتور حذف‌شده همان پاسخ «پیش‌فاکتور یافت نشد» را می‌گیرد.

## ساختار

- `Actions/Wallet/ListCreditUsageAction`: ردیف‌ها و run هر ردیف از `AiWorkflowRunRepositoryInterface::forWorkspaceByIds` (محدود به Workspace). DTOهای `Data/Wallet/CreditUsage` و `CreditUsageLine`. کنترلر اول Policy کیف پول را بررسی می‌کند و بعد Action را صدا می‌زند.
- `Actions/Wallet/ShowTelegramBalanceAction`: متن `/balance`، با همان Policy کیف پول API. سرویس گفتگو دیگر مستقیم به repository کیف پول وابسته نیست. workflow بدون کلاس خروجی ledger را نمی‌شکند و فقط کلاس `null` می‌گیرد.
- `Actions/Wallet/ReconcileCreditLedgerAction` و فرمان `credits:reconcile`. queryها در `EloquentWalletRepository` (`cacheDrift`، `holdsWithSettlements`، `settlementsWithoutHold`).
- ثابت `CreditLedgerEntry::RELATED_RUN` جای رشته تکراری `'ai_workflow_run'` را گرفت.
- بدون migration.

## گزینه‌های ردشده

- **اصلاح خودکار drift:** هر اصلاح اعتبار باید دلیل و اپراتور داشته باشد (E08). اصلاح خودکار یک نقص را پنهان می‌کند.
- **تطبیق در هر درخواست:** هزینه query روی هر کسر، و همان invariantها با قید PostgreSQL و قفل کیف پول از پیش حفظ می‌شوند. بررسی دوره‌ای برای پیدا کردن نقص کد یا دست‌کاری مستقیم DB است.
- **نمایش usage و نرخ در API:** خلاف ADR-042 (یک عدد برای فروشنده). usage در `ai_workflow_runs` برای اپراتور می‌ماند.

## شواهد

PostgreSQL موقت با OpenBao 2.4.1: **۳۸۶ تست / ۵۳۳۷ assertion** در دو اجرای پیاپی، بدون skip. SQLite **۳۵۹ پاس / ۲۷ skip**. Pint و PHPStan بدون خطا. جزئیات و دو آزمون ناپایدار اصلاح‌شده در [گزارش ممیزی](../PROJECT_AUDIT_2026-10-26.md). آزمون‌ها در `ExtractionCreditTest`:
- ledger API و `/balance` پس از یک کسر و یک آزادسازی: پیوند کسر به run، پروژه و کلاس، و تنها یک خط کسر در ربات.
- ردیف جعلی که به run Workspace دیگری اشاره دارد هیچ شناسه‌ای از آن را نشان نمی‌دهد.
- `credits:reconcile` روی ledger سالم صفر یافته دارد. دو آزمون با دست‌کاری مستقیم DB هر دوازده بررسی را با شناسه ردیف درست نشان می‌دهند. خروجی فرمان شکست است، یافته لاگ می‌شود و چیزی اصلاح نمی‌شود.
- retention پیش‌فاکتور: با حد صفر پیش‌فاکتور زنده می‌ماند. در ۱۶۷ ساعت هر دو می‌مانند، در ۱۶۹ ساعت فقط پذیرفته‌شده. دکمه پیش‌فاکتور حذف‌شده «یافت نشد» می‌گیرد و چیزی شروع نمی‌کند.

## بازبینی مستقل

بازبین مستقل P1 و P2 نیافت. یافته‌های P3:
- **(اصلاح شد)** workflow بدون کلاس خروجی کل ledger و `/balance` را با ۵۰۰ می‌شکست. اکنون کلاس `null` می‌گیرد.
- **(اصلاح شد)** کسر روی run ناموفق، آزادسازی run موفق و تسویه‌ای که به run دیگری اشاره کند بررسی نمی‌شدند. دو بررسی تازه اضافه شد.
- **(اصلاح شد)** چهار بررسی و پاسخ دکمه پیش‌فاکتور حذف‌شده آزمون نداشتند.
- **(اصلاح شد)** `KM_RETENTION_CREDIT_QUOTE_HOURS=0` پیش‌فاکتور زنده را پاک می‌کرد. اکنون حداقل عمر پیش‌فاکتور + یک ساعت است.
- **(اصلاح شد)** رمزگشایی نام هر پروژه Workspace را جدا بار می‌کرد. اکنون با run بارگذاری می‌شود.
- **(اصلاح شد)** `/balance` ربات Policy کیف پول را بررسی نمی‌کرد (پیش از این برش هم). اکنون مثل API.
- **(ثبت‌شده)** `cursor()` در pdo_pgsql کل نتیجه را در حافظه نگه می‌دارد. در مقیاس پایلوت مشکلی نیست.
- **(ثبت‌شده)** `/balance` برای ۵ کسر تا ۵۰ ردیف می‌خواند.

## محدودیت‌ها و باز

- reconciliation با صورت‌حساب واقعی provider (Gemini) تطبیق نمی‌دهد. کسر هنوز به usage گزارش‌شده n8n وابسته است.
- هشدار یافته فقط لاگ و خروجی شکست فرمان است. کانال هشدار اپراتور (Admin Panel E10) ساخته نشده است.
- refund پس از capture و adjustment اپراتور با دلیل هنوز ساخته نشده‌اند. هر دو به مسیر و احراز اپراتور نیاز دارند که تصمیم باز است.
- بسته سیاست v4 (پیش‌نویس) دسته‌ای برای ledger اعتبار و پیش‌فاکتور ندارد. نسخه بعدی بسته باید این دو را نام ببرد: ledger و پیش‌فاکتور پذیرفته‌شده تا حذف حساب، پیش‌فاکتور پذیرفته‌نشده ۷ روز. بسته در این تغییر ویرایش نشد.
- داشبورد مصرف وب (Mini App) ساخته نشد. فعلاً API و `/balance` ربات FR-073 را پوشش می‌دهند.
