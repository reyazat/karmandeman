# ADR-025 — ثبت محصول از متن ربات با `/product`

تاریخ: ۲۹ اکتبر ۲۰۲۶. وضعیت: تصمیم فنی برش دهم گام ۳، ادامه [ADR-024](ADR-024-telegram-photo-intake.md) و [ADR-023](ADR-023-product-photos-from-batch-assets.md) (PRD E04، FR-030، FR-033، [DEVELOPMENT_PLAN](../DEVELOPMENT_PLAN.md) گام ۳: «یک محصول ساده از متن/عکس، بدون AI»). **مجوز intake واقعی در production، انتشار یا پایان گام ۲ نیست.**

## زمینه

پس از ADR-024، عکس از ربات به Batch می‌رسید، ولی محصول فقط با API ساخته می‌شد. گام ۳ یک مسیر کامل «متن/عکس → پیش‌نویس محصول» بدون AI می‌خواهد. خواندن آزاد متن (تشخیص نام و قیمت از یک جمله) کار AI در گام ۴ است و اینجا ساخته نمی‌شود.

## تصمیم

۱. **قالب صریح:** `/product` و نام در خط اول، و قیمت اختیاری با واحد در خط دوم:
   ```
   /product کیف چرم مشکی
   ۱۲۰٬۰۰۰ تومان
   ```
   - نام خام به builder می‌رود، پس نرمال‌سازی ADR-017 انجام و متن خام تغییرکرده زیر `originals` نگه داشته می‌شود. نام خالی پس از نرمال‌سازی یا بیش از ۲۰۰ نویسه رد می‌شود.
   - قیمت فقط عدد صحیح (رقم فارسی، عربی یا لاتین) است. جداکننده `,`، `٬` یا `.` فقط بین گروه‌های سه‌رقمی پذیرفته می‌شود، پس `12.5`، `1,5` و `۱۲٫۵` هرگز ۱۲۵ یا ۱۵ خوانده نمی‌شوند و رد می‌شوند. نشانه‌های جهت و ZWNJ صفحه‌کلید فارسی نادیده گرفته می‌شوند. صفر، بیش از ۱۲ رقم، متن یا بیش از دو خط رد می‌شود و ربات قالب را توضیح می‌دهد. چیزی ساخته نمی‌شود.
   - رقم آخر نام هرگز قیمت حدس زده نمی‌شود («کفش سایز ۴۲»)، چون قیمت فقط در خط دوم است.

۲. **واحد قیمت الزامی است:** PRD E04 می‌گوید واحد ورودی همیشه ثبت شود و «مبلغ ۵۰۰» بدون واحد پرسش ایجاد کند. پس قیمت بدون «تومان» یا «ریال» رد می‌شود و ربات واحد را می‌پرسد. واحد برند فرض نمی‌شود. قیمتی که کاربر با واحد تایپ کرده `confirmed` است و پاسخ ربات عدد و واحد را تکرار می‌کند. قیمت نیامده `null` و `price_missing` است، هرگز صفر. متن خام قیمت ذخیره نمی‌شود، فقط عدد و واحد آن.

۳. **عکس‌ها:** عکس‌هایی از همان پروژه که هنوز هیچ `/product` قبلی برنداشته (`assets.claimed_by_product_id`)، حداکثر ۱۰ تا به ترتیب دریافت، به محصول وصل و علامت می‌خورند. پس روال کاربر این است: چند عکس، سپس `/product`، و دوباره. این ستون فقط نشان می‌دهد ربات چه چیزی را واگذار کرده است. فهرست واقعی عکس‌های محصول همان `image_asset_ids` رمزشده نسخه است و اصلاح با API آن را عوض می‌کند، نه این ستون را.

   - تا وقتی عکسی از همین پروژه هنوز در صف import است (ADR-024)، `/product` رد می‌شود و ربات می‌گوید چند لحظه بعد دوباره بفرست. پس عکس در راه به محصول بعدی نمی‌رود.
   - اگر بیش از ۱۰ عکس آزاد باشد، پاسخ ربات می‌گوید بقیه برای `/product` بعدی می‌مانند.
   - ترتیب عکس‌ها ترتیب پایان import است. jobها به ترتیب صف اجرا می‌شوند، ولی retry می‌تواند ترتیب را عوض کند. عکس اصلی را کاربر با API اصلاح می‌کند.
   - همان سقف سرعت بارگذاری (۲۰ در دقیقه برای هر کاربر) برای `/product` هم هست.

۴. **اجرا:** همه چیز داخل تراکنش webhook و پس از قفل ردیف Workspace انجام می‌شود: رضایت، جدیدترین پروژه `collecting_input`، انتخاب عکس‌ها، `CreateManualProductDraftAction` (Policy، بررسی Batch برای عکس‌ها طبق ADR-023، idempotency) و علامت‌زدن عکس‌ها. پس دو `/product` هم‌زمان یک عکس را برنمی‌دارند. کلید idempotency از کلید پیام تلگرام ساخته می‌شود و update تکراری از قبل با `update_id` حذف می‌شود.
   - منشأ همه مقدارها `manual_override` است، چون کاربر آن‌ها را تایپ کرده است.
   - Gate A از ربات در [ADR-026](ADR-026-bot-product-approval.md) اضافه شد.

## محدودیت‌ها و کار باز

- عکسی که با API بارگذاری یا به محصول وصل شده، علامت ربات ندارد و `/product` بعدی می‌تواند آن را دوباره بردارد. پس از reopen پروژه هم همین است. بررسی ADR-023 همچنان مرز Batch را حفظ می‌کند.
- عکس واگذارشده حتی اگر بعداً با API از محصول جدا شود، دوباره به `/product` دیگری داده نمی‌شود.
- انتخاب صریح پروژه، ویرایش و تأیید محصول از ربات، و فیلدهای دیگر (SKU، توضیح، ویژگی) از ربات ساخته نشده‌اند.
- خواندن آزاد متن و جدا کردن چند محصول از یک پیام کار AI گام ۴ است.
