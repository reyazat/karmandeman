## ۱. تصمیم استراتژیک در یک صفحه

### تعریف برند

**کارمند من پلتفرمی برای استخدام، آموزش، مدیریت و نظارت بر کارمندان هوش مصنوعی متخصصِ کسب‌وکار است.** هر کارمند مسئول یک نتیجه مشخص است؛ می‌تواند با صاحب کسب‌وکار گفت‌وگو کند، از حافظه و داده‌های مجاز سازمان استفاده کند، کار چندمرحله‌ای را انجام دهد، خروجی را برای تأیید ارائه دهد و گزارش عملکرد داشته باشد.

### نقطه ورود به بازار (Beachhead)

**اولین کارمند:** «کارمند آماده‌سازی محصول برای فروش دیجیتال» — اطلاعات پراکنده محصولات (عکس، ویس، متن، جدول قیمت) را به **Product Repository ساختاریافته و تأییدشده** و سپس فایل/صفحه آماده استفاده تجاری تبدیل می‌کند.

### ابزار ورود اولیه

**ربات تلگرام = آزمایشگاه بازار و تجربه اولیه تعامل، نه محصول نهایی و نه معماری دائمی.** در آن رفتار، کیفیت، هزینه، رضایت و تمایل واقعی به پرداخت آزموده می‌شود. استفاده از تلگرام به معنی ساخت یک «ربات برای همیشه» نیست.

### مقصد

**پلتفرم وب Karmandeman** با Workspace کسب‌وکار، حافظه مشترک قابل کنترل، کتابخانه داده‌ها، پنل حرفه‌ای مقایسه/بازبینی/ویرایش محصولات، موتور کارهای تکراری، فهرست کارمندان آماده، استخدام/پیکربندی کارمندان و سطوح دسترسی/پرداخت/گزارش یکپارچه. تلگرام بعداً فقط یکی از Channelهای تعامل باقی می‌ماند.

### وعده محصول (Value Proposition)

> **«کارهای پراکنده و وقت‌گیر کسب‌وکارت را به کارمندهای متخصص بسپار؛ آن‌ها تو و کسب‌وکارت را می‌شناسند، درباره ابهام‌ها سؤال می‌کنند و نتیجه‌ای آماده استفاده تحویل می‌دهند.»**

**نسخه مخصوص اولین کارمند:**

> «عکس، ویس یا فایل محصولاتت را بفرست؛ کارمند من با شناخت برندت، اطلاعات را منظم می‌کند و بعد از تأییدت، فایل فروشگاه، کاتالوگ و محتوای فروش آماده می‌دهد.»

### اصل مزیت رقابتی

**From unstructured daily inputs to verified commercial outputs, with reusable organizational memory.**

قدرت محصول نه در تعداد Agent، نه در Prompt Chat، نه در تولید عکس جداگانه؛ بلکه در اتصالِ **داده خام → استخراج قابل ردیابی → تصمیم انسانی → رکورد مشترک → خروجی تجاری قابل استفاده → یادگیری ترجیحات** است.

## ۲. چرا این فرصت ارزش بررسی دارد؟

### ۲.۱ مشکل واقعی کسب‌وکارهای هدف

بسیاری از فروشندگان و صاحبان کسب‌وکارهای کوچک، تمام اطلاعات لازم برای کار را دارند اما نه در قالب قابل استفاده توسط نرم‌افزار: عکس در موبایل، صوت در پیام‌رسان، قیمت در فایل و یادداشت، توضیحات در حافظه افراد، و ترجیحات برند در گفت‌وگوهای پراکنده. راهکارهای نرم‌افزاری سنتی انتظار دارند کاربر داده را قبلاً ساختاریافته و آماده کند؛ این همان کاری است که مشتری شلوغ و کم‌مهارت دیجیتال نمی‌خواهد انجام دهد.

**فرضیه ارزش:** کسب‌وکار حاضر است برای «انجام نتیجه» پول بدهد، نه صرفاً برای دسترسی به یک ابزار AI. این فرضیه باید با پرداخت واقعی و استفاده تکراری تأیید شود.

### ۲.۲ چرا موبایل‌محور؟

- ورودی واقعی غالباً از دوربین، میکروفون و پیام‌رسان شروع می‌شود؛ اصطکاک ثبت داده باید نزدیک به صفر باشد.
- متن طولانی، جدول پیچیده و پنل تنظیمات برای همه کاربران مناسب نیست.
- **چت ابزار کشف نیت و رفع ابهام است**، اما جدول بررسی حجیم در وب/Review View انجام می‌شود.

این یک تعریف UX برای ICP است، نه ادعای آماری درباره «تمام بازار ایران». باید در مصاحبه‌ها اندازه‌گیری شود.

### ۲.۳ چرا اولین محصول کاتالوگ/آماده‌سازی محصول؟

- اطلاعات اولیه غالباً قابل دریافت با عکس/صوت است.
- **قبل/بعد دمو** قابل نمایش است و کیفیت خروجی قابل ارزیابی است.
- خروجی‌ها (CSV، PDF، کاتالوگ آنلاین) به یک نتیجه کاری مشخص متصل‌اند.
- با WordPress/WooCommerce و مسیر ورود اولیه انتخاب‌شده هم‌راستاست.
- داده محصول در Repository می‌ماند و برای خروجی‌های بعدی قابل reuse است.

### ۲.۴ چرا ممکن است جواب ندهد؟

- گروهی از فروشگاه‌ها محصول جدید کمی دارند و نیازشان مقطعی است.
- بسیاری از افراد ترجیح می‌دهند اپراتور موجود یا فریلنسرشان کار را انجام دهد.
- عکس و قیمت به‌قدری نامنظم‌اند که کمک انسانی هزینه را نابود می‌کند.
- کاربران ممکن است از خروجی خوششان بیاید اما حاضر به پرداخت منظم نباشند.
- دسترسی به تلگرام، مدل‌های خارجی و نظام پرداخت می‌تواند مانع واقعی باشد.
- افزونه‌ها و ابزارهای عمومی AI بخشی از قابلیت‌ها را کالایی می‌کنند.

**بنابراین:** محصول از نظر فنی قابل تصور است، ولی درآمد و مزیت پایدار هنوز اثبات نشده‌اند.

| هستیم | نیستیم |

| موتور تبدیل داده خام به نتیجه عملیاتی | مجموعه‌ای از Promptهای آماده و بی‌ارتباط |

| مدل Workflow با تأیید انسانی | «AI کاملاً خودکار و بدون خطا» |

### ضد‌وعده‌های صریح (Claims to avoid)

- «همه کارهای شرکت شما را بدون دخالت انسان انجام می‌دهد.»
- «از روی تصویر، جنس/وزن/قیمت دقیق را می‌فهمد.»
- «به‌صورت خودکار فروش شما را افزایش می‌دهد.»
- «تمام فروشگاه‌های ووکامرس را بدون تست و اصلاح پشتیبانی می‌کند.»
- «هوش مصنوعی کاملاً اختصاصی و غیرقابل کپی داریم.»

این ادعاها هم از نظر کیفیت و هم از نظر اعتبار برند خطرناک‌اند.

## ۴. مشتری هدف، انتخاب بازار و اقتصاد رفتار

### ۴.۱ ICP اولیه: فروشنده با ورود مکرر کالا

**ملاک انتخاب مشتری فقط اندازه کسب‌وکار یا داشتن سایت نیست؛ فرکانس و هزینه آماده‌سازی محصول است.**

**ویژگی مطلوب:**

- حداقل ماهی دو نوبت افزودن/اصلاح محصول، یا Batchهای نسبتا حجیم (فرضیه برای تست).
- صاحب فروشگاه یا اپراتور با موبایل کار می‌کند و از ورود دستی محتوا ناراضی است.
- اطلاعات اولیه به‌صورت عکس/صوت/لیست وجود دارد.
- کاتالوگ برای مشتری یا فایل ورودی سایت واقعاً مصرف می‌شود.
- در فرآیند فعلی، زمان یا هزینه مشهودی صرف ورود و مرتب‌سازی اطلاعات می‌شود.

**اولویت آزمایشی:** کیف و اکسسوری؛ بعد از تأیید، پوشاک و سپس صنف‌های با مشخصات پیچیده‌تر.

### ۴.۲ مشتریان کنار گذاشته‌شده در شروع

- فروشگاه بدون تغییر محصول و بدون تقاضای کاتالوگ‌های مکرر.
- مشتری‌ای که همه داده‌ها را از قبل با فرمت استاندارد آماده دارد و فقط Importer ارزان می‌خواهد.
- کالاهایی که خطای کوچک در تصویر/وزن/قیمت خسارت جدی ایجاد می‌کند (طلا/جواهر در نخستین پایلوت گسترده).
- شرکت‌های بزرگ با ERP و نیاز یکپارچه‌سازی سنگین که چرخه خرید طولانی دارند.

### ۴.۳ Jobs-to-be-Done

| محرک | کاری که مشتری می‌خواهد انجام شود | معیار ارزش |
|---|---|---|
| «محصول جدید رسیده» | ثبت مشخصات و تصاویر برای سایت | زمان از عکس تا محصول آماده |
| «باید کاتالوگ برای مشتری بفرستم» | PDF/لینک حرفه‌ای با قیمت مناسب | سرعت و صحت فایل |
| «قیمت‌ها عوض شده» | نسخه تازه لیست قیمت بدون شروع از صفر | تعداد اصلاحات و جلوگیری از فایل قدیمی |
| «تولید محتوا برای این محصولات می‌خواهم» | خروجی تصویر/استوری/کپشن متناسب برند | میزان استفاده از فایل‌ها |
| «این‌بار هم مثل قبل» | استفاده از حافظه تنظیمات و تصمیم‌ها | کاهش سؤال و زمان onboarding دوباره |

### ۴.۴ یک حقیقت تلخ در درآمد

اگر ارزش ما فقط «ساخت PDF زیبا» باشد، استفاده احتمالاً موردی و رقابت قیمتی شدید می‌شود. ارزش اقتصادی بلندمدت باید از **Product Knowledge Base و چرخه اصلاح، تولید مجدد، انتشار و reuse داده** حاصل شود. اگر داده پایلوت نشان نداد مشتری این چرخه را لازم دارد، نباید با افزودن ده‌ها خروجی تبلیغاتی مسئله را پنهان کنیم.

## ۵. مزیت رقابتی: کجا واقعاً قابل دفاع است؟

### ۵.۱ سطوح تمایز

**سطح ۱ — به‌سادگی کپی‌شدنی:** Prompt، تولید کپشن، حذف پس‌زمینه، PDF Template، چت‌بات ساده. این‌ها قابلیت لازم‌اند اما به‌تنهایی moat نیستند.

**سطح ۲ — دشوارتر اما قابل تقلید:** UX فارسی موبایلیِ ویس/عکس/سؤال حداقلی، پایپ‌لاین تطبیق عکس و قیمت، خروجی تست‌شده برای WooCommerce، قالب‌های صنفی. ارزش واقعی در کیفیت اجرای end-to-end و هزینه پایین اصلاحات است.

**سطح ۳ — دفاع‌پذیری بالقوه:** دیتای تأییدشده محصولات، حافظه تصمیم‌های برند، فرآیندهای تکراری که به کسب‌وکار متصل‌اند، شبکه همکاران راه‌اندازی، history/permissions و switching cost مبتنی بر اعتماد و کارکرد واقعی. این مزیت تنها با **استفاده مکرر و کیفیت بالا** ایجاد می‌شود؛ صرف ذخیره داده قفل‌شدن مشتری یا حق انحصاری نیست.

### ۵.۲ فرمول تمایز پیشنهادی

`مزیت محصول = دقت داده + سرعت تبدیل + سادگی موبایلی + استفاده مجدد + تحویل قابل استفاده + اعتماد`

آزمون سخت: اگر مشتری همان کار را با یک ابزار AI عمومی + افزونه ساده، در همان زمان و با هزینه کمتر انجام دهد، تمایز ما شکست خورده است.

### ۵.۳ رقبا و جانشین‌ها

| دسته | مزیت رقیب/جانشین | پاسخ ما | خطر |
|---|---|---|---|
| ابزارهای عکس/ویدئوی AI (ایرانی و جهانی) | تولید رسانه جذاب و ارزان | خروجی ساختاریافته تجاری + حافظه + چند فرمت | تصویرسازی کالایی می‌شود |
| افزونه‌های WooCommerce و Importerها | اتصال عمیق، هزینه کم | ساخت داده **قبل** از Import؛ نه جایگزین افزونه | مشتری منظم به ما نیاز ندارد |
| تولیدکنندگان محتوای آزادکار | شناخت صنعت و کنترل انسانی | زمان کوتاه‌تر و workflow تکراری + تأیید | کیفیت انسانی ممکن است بهتر باشد |
| دستیاران فروش/CRM | پاسخ و پیگیری مشتری | تمرکز روی Product Intake و نشر | ورود نابجا به بازار شلوغ چت‌بات |
| ابزارهای عمومی AI/Shopify Sidekick | ادغام قوی با پلتفرم و مدل‌های پیشرفته | زبان/جریان‌های واقعی/نیاز بازار هدف + پشتیبانی حضوری | پلتفرم‌های بزرگ ممکن است قابلیت مشابه بسازند |

**نحوه برخورد:** نه جنگ بر سر «بهترین مدل»، بلکه تمرکز بر یک کار با خروجی بررسی‌پذیر و اقتصاد مناسب.

**دسته‌های نمونه برای مطالعه:** Photoroom و NegarAI (تولید رسانه)، Vigent (Agentهای فروش/پشتیبانی)، Shopify Sidekick (دستیار متصل به داده فروشگاه)، محصولات هوشمند حسابداری/اسناد (Vertical AI). نام‌بردن به معنی برتری یا تحلیل قطعی قیمت/درآمد آن‌ها نیست؛ رصد رقبا باید هر فصل به‌روز شود.

## ۶. معماری مفهومی پلتفرم: امروز کوچک، فردا قابل توسعه

```text
                       برند و تجربه کاربر
                      KARMANDEMAN.IR
                              |
              +---------------+---------------+
              |                               |
      کانال آزمون Telegram               پنل وب آینده
       Voice / Image / Chat        Review / Compare / Manage
              |                               |
              +---------------+---------------+
                              |
               هسته مشترک پلتفرم (API-first)
  +----------------------------+---------------------------+
  | Identity / Workspace / Permissions                     |
  | Business Memory (verified + source + consent)          |
  | Employee Registry / Templates / Scoped Tools           |
  | Project / Task / Approval / Audit                      |
  | Product & Asset Knowledge Repository                   |
  | Credits / Subscription / Billing                      |
  | Workflow Execution / Provider Abstraction             |
  +----------------------------+---------------------------+
                              |
      +-----------------------+-----------------------+
      |                       |                       |
  کارمند اول              کارمند دوم              کارمندان بعدی
  آماده‌سازی محصول       [فقط پس از تقاضا]      [پس از اعتبارسنجی]
      |                       |                       |
 Product -> PDF/CSV      حافظه مجاز مشترک      خروجی‌های قابل اندازه‌گیری
```

**مرز اساسی:** حتی در صورت شکست فرضیه کارمند اول، زیرساختی مثل Identity، Workspace، Memory و Workflow قابل reuse است؛ ولی این نباید توجیهی برای گران‌ساختن زودهنگام هسته باشد.

### ۶.۱ دارایی‌هایی که باید بین کارمندان مشترک باشند

- هویت کسب‌وکار و افراد دارای مجوز.
- پروفایل برند، محدودیت‌ها و اهداف تأییدشده.
- کتابخانه کالاها و فایل‌ها، با Permission و نسخه.
- تاریخچه Task و Approval و Audit.
- اعتبار و هزینه مصرف خدمات.

**ولی:** حافظه شخصی افراد، اطلاعات محرمانه و داده محدود به کارمند مالی/حقوقی نباید بی‌قید در دسترس تمام کارمندان باشد. Sharing باید explicit یا policy-based و قابل مشاهده باشد.

### ۶.۲ فلسفه Agent

«یک کارمند = یک مسئولیت تجاری با ورودی، ابزار، اجازه، خروجی و سنجه عملکرد مشخص.»

چند کارمند صرفاً چند Persona در یک چت نیستند. نمونه آینده: کارمند آماده‌سازی محصول وظیفه استانداردسازی دارد؛ کارمند تبلیغات مسئول ساخت کمپین بر پایه داده محصول و سبک برند است؛ کارمند استعلام B2B مسئول آماده‌سازی پیش‌فاکتور بر اساس قیمت تأییدشده است. اگر دو «کارمند» صرفاً دکمه‌های یک workflow باشند، آن‌ها را بی‌جهت دو محصول نفروشیم.

## ۷. ستون فقرات محصول: حافظه و داده ساختاریافته

### ۷.۱ چه چیزی را «حافظه» می‌نامیم؟

| لایه | مثال | نحوه اعتبار |
|---|---|---|
| Workspace Profile | نام برند، صنف، مخاطب، واحد قیمت | تأیید مستقیم کاربر |
| Brand Preferences | لحن، رنگ، عدم نمایش قیمت در PDF | صریح یا از اصلاح تکراری با پیشنهاد تأیید |
| Business Rules | عدم انتشار قبل تأیید، دسته‌بندی‌ها | تنظیم سیاست توسط مالک |
| Product Knowledge | SKU، قیمت، رنگ، عکس، دسته | منبع + نسخه + تأیید فیلد |
| Workflow History | پروژه‌های قبلی، خروجی‌های استفاده‌شده | ثبت عملیاتی قابل حسابرسی |
| Candidate Insights | «معمولاً کاتالوگ بدون قیمت می‌خواهید» | پیشنهاد، نه حقیقت قطعی |

**اصل:** ذخیره کل transcript به‌عنوان «حافظه مفید» کافی نیست و می‌تواند خطا/حریم خصوصی ایجاد کند. دانش استخراج‌شده باید منبع و status داشته باشد و اطلاعات قدیمی قابل ابطال باشد.

### ۷.۲ چرا Product Repository استراتژیک است؟

برای هر کالا یک نسخه مرجع قابل تأیید می‌سازیم. تمام Outputها مشتق از Snapshot مشخص همان داده‌اند:

```text
عکس / ویس / فایل قیمت
           |
       استخراج + سؤال
           |
       رکورد محصول تاییدشده  <-- اصلاح/نسخه‌های جدید
           |
     +-----+----------+--------------+
     |                |              |
 Woo CSV / JSON    PDF/Online     Story / Caption
```

نتیجه: تولید PDF دوم از همان داده ارزان‌تر و سریع‌تر از شروع مجدد است؛ اختلاف قیمت بین PDF و CSV کاهش می‌یابد؛ و وب‌پنل بعدی از داده واقعی استفاده می‌کند.

### ۷.۳ «پیشنهاد شگفت‌انگیز» چگونه واقعاً ساخته می‌شود؟

پیشنهادهای باکیفیت باید بر پایه **واقعیت قابل استناد و موقعیت کاری مشتری** باشند:

- «برای ۱۲ محصول جدید هنوز جنس تأیید نشده؛ این اطلاعات را تکمیل کنیم تا فایل فروشگاه دقیق‌تر شود.»
- «سه پروژه قبل کاتالوگ بدون قیمت خواستی؛ می‌خواهی این‌بار پیش‌فرض همان باشد؟»
- «لیست قیمت تغییر کرده، اما کاتالوگ آنلاین لینک ثابتی دارد؛ نسخه جدید بسازیم؟»

این‌ها در ابتدا **قواعد ساده** هستند، نه AI خودمختار پرهزینه. پیشنهاد باید بگوید «چرا»، «چه خروجی» و «با چه هزینه‌ای»، و هیچ اقدام پولی بدون تأیید اجرا نشود.

**رفتار بد:** پیام‌های فروش مکرر، پیشنهاد بی‌ربط، حدس درباره فروش بدون داده، یادگیری مخفی ترجیحات و حذف اختیار مشتری.

## ۸. تجربه محصول: تلگرام برای کشف، وب برای کنترل

### Telegram Pilot

- `/start`، برند را معرفی کن، ویس/عکس/فایل بفرست، ابهام‌ها را پاسخ بده، Quote را ببین، تأیید کن، خروجی/لینک را بگیر، آرشیو را بخوان.
- کاربر کم‌مهارت لازم نیست JSON یا CSV را بفهمد؛ سیستم کاربرد هر خروجی را توضیح می‌دهد.
- طراحی مکالمه با متن کم و تصمیم‌های روشن؛ فرآیند داده/اعتبار بیرون از Chat State تلگرام است.

### Web Platform Vision

**صفحات کلیدی مقصد:**

1. **Workspace Home:** کارمندان فعال، پروژه‌های نیازمند تصمیم، مصرف اعتبار، پیشنهادهای مستند.
2. **Employee Directory:** استخدام کارمند آماده، مشاهده حدود صلاحیت و هزینه، سفارشی‌سازی قالب کنترل‌شده.
3. **Business Memory:** «آنچه درباره کسب‌وکار شما می‌دانیم»؛ منشأ، تاریخ، سطح دسترسی، تأیید، حذف/اصلاح.
4. **Product Review Grid:** عکس اصلی کنار محصول استخراج‌شده؛ فیلتر خطا، مقایسه دو نسخه، ویرایش گروهی، تأیید.
5. **Product Library:** دسته‌بندی/SKU/ویژگی‌ها/قیمت‌ها/عکس‌ها و تاریخچه تغییر.
6. **Projects & Outputs:** نسخه کاتالوگ، فایل‌های ساخته‌شده، لینک عمومی، دانلود و حذف.
7. **Credits & Billing:** شرح هزینهٔ هر خروجی، میزان استفاده و خطاها.
8. **Workspace Administration:** کاربران، مجوزها، اتصال به WordPress/سرویس‌های دیگر.

### اصل مهاجرت بدون اصطکاک

تمام داده و خروجی‌های تلگرام با همان حساب در وب قابل مشاهده باشند. **کاربر نباید برند را دوباره معرفی کند یا آرشیو پروژه‌ها را از دست بدهد.** هویت وب باید با تأیید امن به حساب Telegram وصل شود و در ادامه امکان ورود مستقل نیز داشته باشد.

## ۹. مدل کسب‌وکار: مرحله‌ای، نه وابسته به تعداد Agent

### ۹.۱ واحد ارزشی که مشتری می‌خرد

برای کارمند اول، «یک محصول آماده» یا «یک بسته خروجی از محصولات تأییدشده» از نظر ذهن مشتری طبیعی‌تر از «توکن AI» است. در Backend می‌توان اعتبار را به هزینه پردازش نگاشت؛ در UX باید قیمت قابل فهم باشد.

**مدل پیشنهادی آغاز:** سهمیه هدیه کوچک + بسته‌های اعتباری متناسب با مصرف؛ قیمت اولیه باید با داده واقعی استخراج، اصلاح، تصاویر و پشتیبانی محاسبه شود. مشتری کم‌مصرف را مجبور به اشتراک ماهانه نکنید.

**پس از اعتبارسنجی:** اشتراک برای کاربران پرتکرار، چند برند، تیم/آژانس، اتصال مستقیم، ابزارهای پیشرفته، API و SLA؛ خدمات Setup جداگانه برای مشتریانی که نیاز دارند.

### ۹.۲ نمونه ریاضی اقتصاد واحد (فرضی، نه قیمت بازار)

تعریف‌ها:

- `Net Revenue/Customer`: مبلغ تحقق‌یافته پس از برگشت/کارمزدهای وابسته به تراکنش.
- `Variable Delivery Cost`: مدل AI، پردازش تصویر/صوت، ذخیره‌سازی متغیر، انتقال فایل، Retry، زمان پشتیبانی قابل انتساب و پرداخت.
- `Contribution = Net Revenue - Variable Delivery Cost`.
- `CAC Payback = CAC / Monthly Contribution`, در صورت Contribution مثبت و ماهانه پایدار.

**مثال فقط برای فهم حساسیت:** اگر یک پروژه ۵۰ قلم داشته باشد و AI در ۱۰ قلم نیازمند دخالت اپراتور شود، «هزینه مدل» ممکن است کوچک باشد ولی کل هزینه خدمت بسیار بالاتر شود. هر یک دقیقه کمک انسانی باید در مدل اقتصادی وارد شود.

**متغیرهای اصلی برای تست:** قیمت پذیرفته‌شده به‌ازای قلم، متوسط تعداد قلم در پروژه، هزینه accepted item، نرخ بازتولید تصویر، Support minutes/order، نرخ سفارش دوم، هزینه جذب، سبد اعتبار مصرف‌شده/هدیه استفاده‌شده، ریزش کاربران و نرخ تبدیل.

### ۹.۳ نقطه بحرانی پرداخت تلگرام

مستند رسمی تلگرام برای **خدمات دیجیتال داخل Bot/Mini App** پرداخت با **Telegram Stars** را لازم می‌داند: <https://core.telegram.org/bots/payments-stars>. پس پیش‌فرض «فروش کردیت ریالی داخل ربات» در شرایط فعلی **تأییدشده نیست** و نباید در Pitch یا بک‌لاگ به‌عنوان امر حل‌شده بیان شود.

**استراتژی کاهش ریسک:**

1. پایلوت اول با اعتبار هدیه محدود و ثبت هزینه واقعی.
2. در هفته اول امکان خرید/مصرف Stars، دسترس‌پذیری در ایران، تسویه درآمد و الزامات مالی/حقوقی بررسی شود.
3. وب‌اپ نهایی کانال مستقل فروش و پرداخت خود خواهد داشت؛ طراحی هر تعامل بین وب و تلگرام باید با سیاست‌های فروش خدمات دیجیتال تلگرام سازگار بررسی شود.
4. اگر مسیر پرداخت متناسب با بازار عملی نباشد، از تلگرام فقط برای اعتبارسنجی UX/تحویل نمونه استفاده شود و آزمایش پرداخت واقعی از تجربه مستقل وب آغاز شود؛ **نه طراحی دورزدن پرداخت درون تلگرام**.

**این تصمیم Go/No-Go پولی است، نه جزئیات فنیِ آخر پروژه.**

### ۹.۴ NextPay: مسیر تأییدشده فنی برای وب، نه معافیت از Stars در تلگرام

**یافته تحقیق:** نکست‌پی (`nextpay.org`) درگاه ریالی وب‌سرویس، لینک پرداخت قابل اشتراک در شبکه‌های اجتماعی از جمله تلگرام، و API پرداخت با واحد تومان (`IRT`) یا ریال (`IRR`) ارائه می‌کند. پس برای وب‌اپ مستقل کارمند من یک گزینه عملی برای **آزمایش اتصال و پذیرندگی** است. اینکه نکست‌پی لینک پرداخت «مناسب تلگرام» ارائه می‌دهد، به‌خودی‌خود مجوز فروش کردیت خدمات دیجیتال در داخل ربات Telegram محسوب نمی‌شود. طبق شرایط تلگرام، خرید دیجیتال درون Bot/Mini App باید از Stars استفاده کند.

**سیاست محصول:**
- **مسیر تلگرام:** UX، اعتبار هدیه، یادگیری و دریافت فیدبک؛ پرداخت پولی درون تلگرام فقط با روش سازگار (برای خدمات دیجیتال، Stars) پس از بررسی تجربه کاربر ایرانی و امکان تسویه.
- **مسیر وب مستقل:** بررسی و در صورت پذیرش نوع فعالیت، اتصال NextPay برای فروش قانونی ریالی؛ پرداخت و کیف پول از طریق Billing مشترک، مستقل از کانال تعامل.
- **پرهیز از فرض نادرست:** لینک‌دادن از Bot برای خرید اعتبار وب نباید به‌عنوان راه‌حل سازگارِ قطعی یا روش دورزدن محدودیت Stars طراحی شود. قبل از اجرای چنین مسیرهای متصل، ارزیابی حقوقی و سیاست پلتفرم لازم است.
- **گیت فعال‌سازی:** تأیید پذیرندگی خدمات AI/کردیت، Verify سمت سرور، ثبت اتمیک و بدون تکرار اعتبار، refund/reconciliation و تست پرداخت واقعی با کاربر نمونه.

منابع: <https://nextpay.org/faq/>، <https://nextpay.org/nx/docs>، <https://core.telegram.org/bots/payments-stars>.

## ۱۰. مسیر ورود به بازار (GTM)

### مرحله A — Design Partners

- جذب ۵–۱۰ فروشگاه واقعی، با تنوع مهارت دیجیتال، حجم ورود کالا و داشتن/نداشتن وب‌سایت.
- گرفتن اجازه برای نمونه واقعی؛ اگر داده محرمانه است با داده جایگزین/ناشناس.
- اندازه‌گیری «امروز چطور کار می‌کنی؟» نه فقط «از AI خوشَت می‌آید؟».
- هدف: ۱۰۰ قلم داده متنوع، حداقل چند پروژه واقعی با استفاده اثبات‌شده.

### مرحله B — اثبات ارزش در یک جمله

دموی فروش نباید «ما مدل‌های پیشرفته AI داریم» باشد. دمو باید نشان دهد: ورودی خام واقعی مشتری، ابهام‌سنجی، تأیید، CSV/PDF قابل استفاده؛ مدت‌زمان و میزان اصلاح را با روش فعلی او مقایسه کند.

### مرحله C — کانال توزیع

- **فروش مستقیم محدود** برای کشف دقیق مسئله و بهبود UX.
- **همکاران وردپرس و آژانس‌ها** فقط بعد از استانداردشدن Setup؛ برای نصب/آموزش/اعتماد کانال بالقوه‌اند.
- مدل همکار باید زمان Setup، درآمد خالص پس از کمیسیون و کیفیت مشتری جذب‌شده را بسنجد.
- تبلیغات عمومی وسیع پیش از اثبات فعال‌سازی و بازگشت استفاده، هدررفت بودجه است.

### Positioning اولیه

**برای صاحب فروشگاه شلوغی که محصولاتش در عکس و پیام و فایل پراکنده است، کارمند آماده‌سازی محصولِ کارمند من، داده را به محصول قابل تأیید و خروجی فروش آماده تبدیل می‌کند؛ بدون نیاز به یادگیری چند ابزار مستقل.** برخلاف عکس‌ساز یا Importer تنها، فرایند ورودی تا تحویل و حافظه قابل استفاده را یکپارچه می‌کند.

## ۱۱. نقشه راه محصول با «دروازه شواهد»

### نمای کلان

```text
                           چشم‌انداز بلندمدت
                 Platform for Specialized AI Employees
                                  ▲
                                  │  P4 — Marketplace / Builder
                                  │       فقط پس از استانداردشدن الگوها
                                  │
                     P3 — Multi-Employee Platform
                          Shared Memory + Employee Registry
                                  ▲
                                  │  پاداشِ اثبات نیاز به کارمند دوم
                                  │
                  P2 — Professional Web Workspace
                  Review Grid + Product Compare + Integrations
                                  ▲
                                  │  پاداشِ نیاز واقعی به بررسی دسته‌ای
                                  │
                   P1 — Telegram First Employee Pilot
                   Product Intake -> Verified Data -> Outputs
                                  ▲
                                  │  پاداشِ داده و نیاز واقعی مشتری
                                  │
                    P0 — Discovery & Concierge Test
```

### جدول فازها

| فاز | افق زمانی تقریبی* | هدف | Deliverable | Gate خروج |
|---|---|---|---|---|
| **P0** Discovery | هفته ۱–۲ | فهم مسئله/نوع ورودی/هزینه | مصاحبه، دیتاست نمونه، نمونه‌سازی نیمه‌دستی، تصمیم پرداخت | مسئله پرتکرار و نمونه داده واقعی |
| **P1** Telegram MVP | هفته ۳–۱۲ | تست UX/کیفیت/مصرف | یک کارمند، برند، Repo محصول، CSV/PDF/JSON، حافظه، اعتبار هدیه، آرشیو | خروجی استفاده‌شده + کیفیت کافی + هزینه قابل قبول |
| **P1.5** Pilot Optimization | ۱–۳ ماه پس از MVP | افزایش اعتماد و بازگشت | به‌روزرسانی نسخه، رفع خطا، قالب‌های پرتکرار، پرداخت مجاز | سفارش دوم و شواهد willingness-to-pay |
| **P2** Web Workspace | پس از Gate و تأمین منابع | مدیریت حجم و کیفیت | Review/Compare Grid، Bulk Edit، Product Library، نسخه‌ها، اتصال ووکامرس بعد از تست | کاهش زمان بازبینی، retention و اقتصاد مثبت |
| **P3** Multi-employee | پس از شناخت Workflow دوم | انتقال ارزش حافظه بین کارمندان | Employee Directory، permissions، shared memory، کارمند دوم قابل اندازه‌گیری | تقاضای واقعی و درآمد افزایشی از کارمند دوم |
| **P4** Builder/Marketplace | بلندمدت و مشروط | مقیاس ارائه و توسعه قالب‌ها | Custom Agent Builder محدود، Template Governance، Marketplace در صورت نیاز | استفاده واقعی چند عمودی و قابلیت کنترل کیفیت |

`*` زمان‌ها افق‌های فرضی و **وابسته به شواهد** هستند. نباید P2 صرفاً به‌خاطر گذشت ۱۲ هفته شروع شود.

### فاز P2 را چطور تعریف می‌کنیم؟

**وب‌اپ باید بهتر از چت در مسئله‌ای مشخص باشد:** مقایسه استخراج با منبع اصلی، بررسی صدها ردیف، ویرایش گروهی، مدیریت تعارضات قیمت، تاریخچه SKU، Bulk Publish Approval و مشاهده اختلاف نسخه‌ها. نباید صرفاً ظاهر زیباتری از ربات ارائه کند.

### کارمند دوم چطور انتخاب می‌شود؟

فقط پس از مشاهده کار واقعی در داده پایلوت:

- اگر مشتری پیوسته از محصول موجود **کپشن/کمپین** می‌خواهد → «کارمند تولید کمپین» قابل آزمون.
- اگر تقاضای اصلی او **پیش‌فاکتور B2B از صوت و عکس** باشد → «کارمند آماده‌سازی استعلام و پیش‌فاکتور» احتمالاً ارزش اقتصادی بالاتری دارد، اما Price Master و خطای مالی باید کنترل شود.
- اگر تقاضا صرفاً یک دکمه/قالب جدید در کارمند اول است → **کارمند دوم نسازید.**

**معیار انتخاب:** Job جدید و مسئولیت متمایز + تکرار مسئله + willingness-to-pay + ابزار/دسترسی مستقل + سنجه نتیجه.

### معیارهای پیشنهادی اولیه

- حداقل ۵ مشتری استفاده واقعی از خروجی را تأیید کنند.

- پس از لحاظ AI، فایل، عکس، Retry و پشتیبانی، Contribution Margin مثبت و رو به بهبود باشد.
- مسیر پرداخت سازگار و عملی برای بازار هدف وجود داشته باشد.

این‌ها معیارهای پیشنهادی مدیریت‌اند و بنچمارک آماری اثبات‌شده نیستند.

## ۲۰. استراتژی فناوری، مالکیت داده و Deployment — تصمیم نسخه ۱.۲

> هدف این فصل هم‌راستا کردن سرمایه‌گذاری فنی با چشم‌انداز پلتفرم است، نه تعیین کاربرپسند بودن فریم‌ورک. مشخصات اجرایی و چک‌لیست‌های عملیاتی در PRD §۲۳ و Runbook مکمل هستند.

### ۲۰.۱ تصمیم نهایی برای فاز اعتبارسنجی

**پلتفرم مرکزی را با Laravel 13 / PHP 8.4 و PostgreSQL 17 می‌سازیم؛ از n8n پایدار 2.44.6 برای آزمایش و اجرای Workflowهای AI استفاده می‌کنیم؛ صف، حساب، حافظه، محصولات، اعتبار و فایل‌ها مستقل از n8n می‌مانند.** زیرساخت آغازین Ubuntu 24.04 LTS + Docker Compose v2 + Redis 7.2 + Caddy 2/TLS و Object Storage خصوصی است. این نسخه‌ها baseline تصمیم در ۲۶ اکتبر ۲۰۲۶ بوده و imageهای واقعی در هر انتشار به digest پین می‌شوند.

**چرا این انتخاب قابل دفاع است؟** n8n زمان یادگیری و اصلاح جریان‌های extraction/transcription/copywriting را کم می‌کند. Laravel امنیت، مالکیت اطلاعات، کنترل مالی و قابلیت توسعه رابط وب را حفظ می‌کند. داده‌های اصلی و حافظه به ابزار orchestration وابسته نمی‌شوند؛ در صورت نارضایتی از n8n می‌توان Workflow را بازنویسی کرد بدون مهاجرت موجودیت‌های اصلی محصول.

### ۲۰.۲ نقشه توسعه فناوری به موازات نقشه محصول

| Gate محصول | زیرساخت هدف | چه چیزی را عمداً نمی‌سازیم؟ |
|---|---|---|
| P0 Discovery | محیط local/staging با نمونه محدود، AI provider benchmark، Docker image قابل بازتولید | High Availability، microservice، vector store |
| P1 Telegram Pilot | Laravel API، n8n داخلی، ۲ دیتابیس منطقی مجزا، Redis/Horizon، bucket خصوصی، backup/monitoring، TLS | پنل محصول کامل، Kubernetes، پرداخت ناهمخوان با سیاست تلگرام |
| P1.5 Retention | نسخه‌های محصول، export cache، هزینه واقعی هر run، بازبینی گردش‌کارها، DR drill | افزودن بی‌دلیل سرور یا کارمند AI |
| P2 Web Workspace | Auth وب، Review Grid، Compare/Bulk Edit، pagination، مستندسازی public API، worker مستقل در صورت فشار | بازنویسی backend از صفر |
| P3 Multi-Employee | Employee Registry، capability permissions، حافظه scopeدار و observability برای هر کارمند | memory آزاد و بدون مرز، multi-agent خودمختار بدون کنترل |
| P4 Builder | ابزار ساخت محدود و قابل نظارت، workflow governance و مجوز تجاری بررسی‌شده | در اختیار گذاشتن editor داخلی n8n به مشتری بدون بررسی حقوقی/امنیتی |

### ۲۰.۳ هزینه زیرساخت، ریسک‌ها و قاعده سرمایه‌گذاری

- آغاز با یک VPS **۴ vCPU / ۸ GiB / حدود ۸۰–۱۲۰ GiB SSD** و Object Storage بیرونی، صرفاً فرض ظرفیت یک پایلوت کوچک و دارای سقف مصرف است؛ هزینه واقعی تابع منطقه میزبان، ترافیک، مدل‌های AI، حجم رسانه و تعداد job هم‌زمان است. قیمت یا SLA بازار از این اعداد استنباط نشود.
- **هزینه اصلی ممکن است compute VPS نباشد**؛ APIهای تصویر/صوت، بازتولیدهای ناموفق، دانلود/ذخیره رسانه، پشتیبانی انسانی و وابستگی به provider خارجی می‌توانند غالب شوند. بنابراین سقف هزینه هر task و پایش هزینه پذیرفته‌شده از روز اول لازم است.
- استقرار یک‌سروری Compose **HA نیست**. Gate مهاجرت به ساختار چندسروری با شواهد واقعی (queue wait، p95 latency، incident، CPU/RAM/IO و نیاز SLA) فعال می‌شود.
- اعتبارسنجی مشتریان ایرانی نیازمند تست واقعی دسترسی تلگرام، سایت عمومی، دامنه، پرداخت و AI provider است؛ انتخاب صرفِ دیتاسنتر در خارج یا داخل ایران به‌خودی‌خود موفقیت شبکه‌ای/حقوقی را تضمین نمی‌کند.

### ۲۰.۴ مرز مالکیت و عدم وابستگی

**دارایی‌های دائمی کارمند من:** `Workspace`, `BrandMemory`, `Product`, `ProductRevision`, `Project`, `TaskRun`, `Approval`, `Asset`, `CatalogVersion`, `WalletLedger` و رویدادهای محصول. این داده‌ها در Backend و Object Storage متعلق به محصول‌اند.

**دارایی‌های تعویض‌پذیر:** Workflowهای n8n، مدل Speech-to-Text/Vision/Text، renderer PDF، کانال Telegram و قالب‌های طراحی. هرکدام باید قرارداد ورودی/خروجی صریح و قابل تست داشته باشند.

**قاعده سرمایه‌گذاری:** هر قابلیت تازه باید یا زمان دستی مشتری را کم کند، یا درصد خروجی پذیرفته‌شده را بالا ببرد، یا هزینه عملیاتی واقعی را کم کند. افزودن پیچیدگی معماری به‌خودی‌خود مزیت رقابتی نیست.

### ۲۰.۵ سیاست عملیاتی حداقلی پیش از آغاز پایلوت

- محیط staging جدا، secrets جدا، backup خارج از سرور با restore test، TLS و پایش runtime/queue و هزینه مدل الزامی است.
- پیش از داده واقعی پایلوت، نیازمندی‌های PRD FR-084…088 و QA-19…21 برای رمزنگاری خصوصی و حذف کامل آزموده شوند. صفحه محدود حریم خصوصی حساب/Telegram Mini App با دکمه حذف در همین gate است؛ مجوز ساخت پنل کامل وب نیست. سقف بکاپ ۱۴ روز و حذف کامل تا ۷ روز از درخواست تأییدشده تصمیم نهایی مالک در [ADR-011](adr/ADR-011-seven-day-complete-erasure.md) است؛ سیاست روی کاغذ اثبات اجرای پاک‌سازی نیست.
- دسترسی n8n Editor و DB/Redis عمومی نیست؛ Workflowهای AI از API داخلی داده scoped می‌خوانند و اجازه تغییر داده مالی ندارند.
- از قبل RPO هدف ≤۲۴ ساعت و RTO هدف ≤۸ ساعت برای پایلوت تعیین شده، ولی تنها **پس از drill عملی** قابل تأیید است.
- وضعیت نهایی مجوز استفاده از n8n، شرایط سرویس AI، درگاه NextPay در وب و الزامات Telegram Stars پیش از فروش پولی باید ثبت شود.
- انتشارها باید قابل بازتولید با `composer.lock`, `package-lock.json`, tagged images + digests و آزمون migration باشند.

**سند عملیات مرجع:** `Karmandeman_Deployment_Runbook_v1.1.md`. **اصل بنیادین:** Telegram و n8n برای اعتبارسنجی به کار می‌روند؛ Laravel، حافظه و داده مشتری بستر پلتفرم بلندمدت‌اند.

## ۲۱. Governance کیفیت مهندسی در طول نقشه راه — نسخه ۱.۳

**اصل:** «سرعت اعتبارسنجی» به معنی پذیرفتن ساختار موقت و ناسازگار نیست. یک **Modular Monolith Laravel** با معماری Action/Repository/Service و Vue 3 + TypeScript feature-first، امکان آزمایش سریع در تلگرام و انتقال کم‌هزینه به وب را فراهم می‌کند. استاندارد الزام‌آور در `Karmandeman_Engineering_Standards_v1.0.md` و الزامات عملیاتی در `Karmandeman_Deployment_Runbook_v1.1.md` آمده‌اند؛ سند استراتژی جایگزین مشخصات کلاس‌ها نیست.

| مرحله | تعهد کیفیت مهندسی | چیزهایی که عمداً به تعویق می‌افتد |
|---|---|---|
| P0 Discovery | نمونه داده واقعی + قرارداد Product JSON و Schema، lint/tests اولیه، thin controller و Action | Agent Builder، UI جامع، microservice |
| P1 Telegram Pilot | Laravel `Actions/{Feature}`، Requests/Resources، Repository Contracts، DI، secured n8n، API versioned، CI tests | ساخت همه feature folderهای آینده بدون نیاز؛ پنل بزرگ |
| P1.5 Retention | tests مالی/tenant، معیار کیفیت خروجی، rollback و upgrade discipline | abstractionهای بی‌کاربرد و general-purpose workflow platform |
| P2 Web Workspace | Vue 3/TS feature modules، Pinia/Router، typed API DTO، Review/Compare/Batch Edit، mobile/RTL tests | تکرار domain rule در Frontend |
| P3 Multi-Employee | Actions و capability permissions برای هر کارمند، Scoped Memory، background workflow events | دسترسی بدون محدودیت به حافظه تمام کسب‌وکارها |
| P4 Builder/Marketplace | extension contracts و governance، isolated execution و versioned APIs | expose کردن n8n editor یا mixed-tenant plugin بدون بررسی |

**Governance:** Tech Lead مالک استاندارد، PR Review و Architecture Decision Record است. Product Owner مالک دامنه/اولویت Feature است. QA مالک تست پذیرش و regression است. تنها استثناها با ADR مکتوب، اثر روی امنیت/مالی و تاریخ بازبینی پذیرفته می‌شوند. DRY/KISS مهم‌اند: لایه‌بندی استاندارد الزام است ولی افزودن Service، abstraction یا interface غیرضروری صرفاً برای پیچیده‌کردن محصول ممنوع است.

**نتیجه استراتژیک:** اولین کارمند را بدون بدهی ساختاری مخرب اعتبارسنجی می‌کنیم، اما روی زیرساخت چندکارمندی قبل از اثبات بازار سرمایه‌گذاری سنگین نمی‌کنیم. API، حافظه، داده محصولات و wallet مستقل از کانال‌اند؛ n8n و Telegram تعویض‌پذیر باقی می‌مانند.
