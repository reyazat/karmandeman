## ۰. خلاصه اجرایی و اصول تغییرناپذیر

**کارمند من یک پلتفرم استخدام و مدیریت کارمندان AI است.** ربات تلگرام فقط **کانال آزمون و اعتبارسنجی اولین کارمند** است؛ برند یا معماری نباید به تلگرام یا تولید PDF محدود شود. اولین کارمند: **«کارمند آماده‌سازی محصول برای فروش دیجیتال»**.

**وظیفه کارمند:** تبدیل عکس، ویس، متن و فایل‌های خام فروشنده به **رکوردهای محصول ساختاریافته و قابل اعتماد**، رفع ابهام با کمترین پرسش، دریافت تأیید و تولید خروجی‌های قابل استفاده مانند CSV ووکامرس، PDF، کاتالوگ آنلاین و محتوای تصویری استاندارد.

### تصمیم‌های قطعی محصول

1. **مرکز ثقل داده = Product Repository**، نه پیام تلگرام و نه فایل PDF. فایل‌ها از نسخه مشخص محصول تولید می‌شوند.
2. **Chat-first, not chat-only:** تلگرام برای ورودی و گفتگو؛ در پایلوتِ خیلی کوچک، بررسی با دکمه/پیش‌نمایش؛ برای ویرایش دسته‌ای یک **Review Web View سبک و موبایلی** در صورت نیاز. پنل جامع وب مقصد بعدی است، نه دامنه MVP.
3. **Workflow-first, AI-assisted:** مدل فقط برای ادراک، استخراج، پیشنهاد متن و گفت‌وگو؛ پول، وضعیت، مجوز، محاسبات، خروجی CSV و صورتحساب با کد قطعی.
4. **Human approval:** قیمت، SKU، تعداد، جنس و مشخصات محصول و نسخه نهایی باید پیش از صدور خروجی قابل انتشار تأیید شوند. **انتشار مستقیم در سایت خارج از MVP است.**
5. **حافظه سازمانی قابل کنترل:** دانش صریح یا تأییدشده برند و ترجیحات، با منبع، نسخه و مجوز؛ نه انتقال خودکار هر جمله به حافظه دائمی.
6. **Backend مستقل از کانال:** Telegram Adapter فقط یکی از رابط‌هاست. حساب کسب‌وکار، پروژه، فایل، کارمند، حافظه، اعتبار و رخدادها در سرویس مرکزی قرار دارند.
7. **پایلوت کوچک و متمرکز:** شروع ترجیحی با کیف و اکسسوری (ویژگی‌های نسبتا ساده)؛ محصولات حساس مثل طلا/جواهر و قیمت لحظه‌ای فاز نخست نیستند.
8. **مزیت رقابتی ادعایی نیست؛ آزمودنی است:** آیا کاربران ورودی خام می‌فرستند، خروجی را واقعاً استفاده می‌کنند، برای سفارش دوم بازمی‌گردند و هزینه پشتیبانی/تولید مقرون‌به‌صرفه است؟

### هشدار حیاتی — پرداخت داخل تلگرام

طبق **مستندات رسمی Telegram برای خدمات دیجیتال**، فروش خدمات/اعتبار دیجیتال داخل Bot و Mini App باید با **Telegram Stars (XTR)** انجام شود؛ فروش از طریق درگاه ریالی در تجربه درون تلگرام را **نباید به‌عنوان راهکار سازگار فرض کرد**، حتی اگر صفحه پرداخت خارجی وجود داشته باشد. این مسئله به‌ویژه برای مخاطب ایران می‌تواند مانع تجاری جدی باشد. راهبرد آزمایشی: ابتدا **اعتبار هدیه محدود + پایلوت دستی/رایگان یا آزمون پرداخت مجاز پس از بررسی شرایط**؛ برای درآمد ریالیِ وب‌محور، جریان مستقل وب را جداگانه از منظر شرایط تلگرام، پرداخت‌یار و حقوقی ارزیابی کنید. هیچ الگوی دور زدن مقررات پرداخت در PRD مجاز نیست. تصمیم نهایی در §۲۰ یک **Go/No-Go** است.  
مرجع: <https://core.telegram.org/bots/payments-stars>


### بررسی تکمیلی ارائه‌دهنده پرداخت — NextPay (۲۵ اکتبر ۲۰۲۶)

**گزینه پیشنهادی برای کانال وب مستقل:** نکست‌پی (`https://nextpay.org/`) با درگاه وب‌سرویس، لینک پرداخت و صفحات پرداخت ریالی. بر اساس مستندات رسمی سرویس، API امکان `IRT`/`IRR` دارد؛ روش استاندارد شامل ساخت تراکنش، هدایت به درگاه، بازگشت و **استعلام موفقیت سمت سرور** است. نکست‌پی همچنین امکان استفاده از لینک پرداخت در کانال‌هایی مانند تلگرام را تبلیغ می‌کند، ولی این صرفاً **قابلیت فنی ارسال/استفاده لینک** را تأیید می‌کند، نه انطباق فروش خدمات دیجیتال *داخل* Bot/Mini App با مقررات تلگرام.

**تصمیم معماری:** از ابتدا `PaymentProvider` مستقل تعریف شود و NextPay به‌عنوان اولین `WebPaymentAdapter` پیاده‌سازی گردد؛ وضعیت اتصال در پرداخت مستقل وب و پرداخت داخل Telegram یکسان فرض نشود. `wallet_ledger` برای هر دو کانال مشترک است، ولی ثبت اعتبار فقط پس از تأیید قطعی پرداخت صورت می‌گیرد.

**پیش‌نیاز فعال‌سازی NextPay (وب مستقل):** تأیید پذیرندگی نوع فعالیت AI/اعتبار دیجیتال، الزامات هویتی/مجوزی، جریان قانونی فروش اعتبار، کارمزد/تسویه و شرایط رسیدگی به استرداد؛ تست `POST /nx/gateway/token`، پرداخت، `callback_uri` و `POST /nx/gateway/verify` در محیط مناسب. پاسخ callback به‌تنهایی اثبات پرداخت نیست. مبلغ/ارز/شناسه سفارش/شناسه تراکنش با رکورد سرور تطبیق یابد و شارژ کیف پول **یک‌بار و اتمیک** انجام شود؛ callback تکراری/تأخیری، قطعی شبکه، refund و reconciliation دوره‌ای پوشش داده شوند. مطابق مستندات نکست‌پی تأیید تراکنش دارای پنجره زمانی محدود است؛ تیم باید زمان‌بندی و محدودیت فعلی را پیش از اجرا دوباره تست کند.

**محدودیت Telegram:** مستند رسمی تلگرام فروش خدمات دیجیتال *درون* Bot/Mini App را منحصراً با Telegram Stars مقرر می‌کند؛ داشتن درگاه نکست‌پی روی وب، این الزام را لغو نمی‌کند. از جریان ارسال لینک ریالی داخل ربات برای خرید اعتبار AI به‌عنوان مسیر تأییدشده یا دورزدن مقررات استفاده نشود. پایلوت تلگرام می‌تواند با اعتبار هدیه انجام شود و فروش مستقل وب پس از بررسی حقوقی/سیاست پلتفرم به‌طور جداگانه آزمایش شود.

**منابع اولیه:**
- مستند API نکست‌پی: <https://nextpay.org/nx/docs>
- امکانات و لینک پرداخت: <https://nextpay.org/> و <https://nextpay.org/faq/>
- پرداخت خدمات دیجیتال تلگرام: <https://core.telegram.org/bots/payments-stars>
- مقررات توسعه‌دهندگان تلگرام: <https://telegram.org/tos/bot-developers>

## ۱. مسئله، بازار و فرضیات

### ۱.۱ مسئله مشتری

مشتری اولیه فروشنده‌ای کم‌وقت، عمدتاً موبایل‌محور و بدون تمایل به کار طولانی با پنل‌های حرفه‌ای است. اطلاعات محصولات در عکس موبایل، پیام صوتی، متن پراکنده، تصویر برگه قیمت یا فایل Excel/CSV قرار دارد. تبدیل دستی این‌ها به نام/توضیح/مشخصات/قیمت/عکس/کاتالوگ/ورودی فروشگاه زمان‌بر و مستعد خطاست.

### ۱.۲ بخش مشتری پایلوت

- **اصلی:** کسب‌وکارهای ایرانی کیف و اکسسوری با حداقل یک جریان ورود محصول جدید و نیاز به محتوای چندکاناله؛ برخی دارای WooCommerce، برخی بدون سایت.
- **فرعی برای مشاهده:** آژانس یا اپراتور فروشگاهی که محتوای چند فروشگاه را آماده می‌کند؛ نباید نیازهای چندمستاجری آژانس محصول اولیه را پیچیده کند.
- **حذف موقت:** کالاهای دارای مقررات/قیمت متغیر سریع یا ریسک صحت تصویر بالا؛ ماشین‌آلات با مشخصات پیچیده؛ سرویس‌های چندزبانه و چندارزی.

### ۱.۳ فرضیات قابل ابطال

| شناسه | فرضیه | آزمون | سیگنال منفی |
|---|---|---|---|
| H1 | ارسال عکس/ویس از تکمیل فرم آسان‌تر است | مشاهده شروع تا اولین پروژه | اکثریت به کمک انسانی مستمر نیاز دارند |
| H2 | محصول از ورودی واقعی با پرسش محدود استخراج می‌شود | حداقل ۱۰۰ قلم واقعی پایلوت | نرخ اصلاح اساسی بسیار بالا |
| H3 | خروجی قابل استفاده تجاری است | استفاده واقعی از PDF/CSV نزد مشتری | فایل‌ها فقط مشاهده می‌شوند و استفاده نمی‌شوند |
| H4 | مشتری مصرف تکراری دارد | سفارش دوم طی ۳۰–۶۰ روز | بازگشت بسیار کم خارج از مشتریان تک‌سفارشی |
| H5 | اقتصاد واحد مثبت می‌شود | Cost per accepted product + support | نیاز دائمی به اپراتور انسانی یا بازتولید متعدد |
| H6 | خرید اعتبار برای مشتری قابل فهم/قابل اجراست | تست بسته‌بندی و پرداخت مجاز | نفهمیدن قیمت یا مانع جدی پرداخت Stars |

## ۲. اهداف و موارد خارج از دامنه

### ۲.۱ اهداف P0

- ثبت‌نام در تلگرام، ساخت یک Workspace و فعال‌سازی کارمند اول.
- آشنایی مکالمه‌ای با برند، لوگو، مخاطب، لحن و قواعد؛ **بدون کسر اعتبار در مرحله تنظیم پایه**.
- ثبت یک پروژه جدید از ترکیب عکس + متن + ویس و فایل جدولی ساده.
- استخراج رکورد محصولات، نگه‌داری منابع و اطمینان/ابهام هر ویژگی، طرح پرسش‌های کم‌تعداد و اولویت‌دار.
- بررسی و تأیید رکورد و خروجی با دو سطح تأیید: داده محصول، سپس بسته خروجی/هزینه.
- تحویل **CSV سازگار با WooCommerce** برای محصول ساده، **PDF فارسی قالب ثابت**، **JSON ساختاریافته و ZIP فایل‌ها** و **لینک کاتالوگ آنلاین**. تصاویر محصول: اصلاح غیرمولد سبک در P0؛ قالب استوری ساده در P1 با شرط ظرفیت.
- آرشیو پروژه‌ها، محصولات و خروجی‌ها؛ دانلود مجدد طی دوره نگهداری اعلام‌شده.
- کیف پول اعتباری قابل حسابرسی با هدیه، رزرو، مصرف و برگشت؛ **خرید اعتبار فقط پس از تصمیم پرداخت سازگار**.
- لاگ عملیات، قابلیت بررسی/اصلاح اپراتور، اندازه‌گیری KPI و اخذ بازخورد.

### ۲.۲ خارج از دامنه P0

- Agent Builder آزاد، Marketplace، اجرای خودمختار چندایجنتی.
- اتصال مستقیم و انتشار بدون تأیید در ووکامرس؛ سینک لحظه‌ای قیمت/موجودی.
- تولید ویدئو، مانکن مجازی، رندر تصویر محصولِ ساختگی با تغییر ویژگی واقعی.
- پشتیبانی همه اصناف، داده‌های کاملاً نامحدود، OCR دست‌نویس با تضمین دقت.
- تحلیل فروش، CRM، پیش‌بینی تقاضا، فروش درون ربات به مصرف‌کننده نهایی.
- پنل کامل وب و مدیریت پیشرفته تیمی؛ نسخه P0 فقط یک مدیر Workspace.

### ۲.۳ اولویت‌بندی

- **P0 — ضروری برای اعتبارسنجی**: UX ثبت‌نام، پروفایل برند، Intake، بازبینی، CSV/PDF/JSON، فایل‌ها، تاریخچه، اعتبار آزمایشی، گزارش رخداد.
- **P1 — پس از مشاهده نیاز واقعی**: تصویر اصلاح‌شده پیشرفته، قالب استوری، Review Web View، نسخه جدید کاتالوگ از داده قبلی، ویرایش دسته‌ای، فایل XLSX، محصولات متغیر در ووکامرس.
- **P2 — مقصد پلتفرم**: وب‌اپ کامل، اتصال مستقیم سایت، چند کارمند، نقش‌های تیمی، پیشنهاددهی پیش‌دستانه و Builder کنترل‌شده.

## ۳. پرسونا، Jobs-to-be-Done و سناریو

### پرسونای A: فروشنده موبایل‌محور

- ۲ تا ۵۰ قلم جدید در هر نوبت (فرض آزمایشی، نه آمار بازار).
- از تلگرام، دوربین و فایل‌های پیام‌رسان استفاده می‌کند؛ مرتب‌سازی دستی سخت است.
- نیاز: «مثل دفعه قبل از این عکس‌ها، فایل سایت و کاتالوگ آماده کن».
- معیار موفقیت: بدون نیاز به کامپیوتر و بدون توضیح دوباره تنظیمات برند، فایل قابل استفاده بگیرد.

### پرسونای B: مدیر فروشگاه ووکامرس

- نیاز به داده تمیز، SKU، دسته و ویژگی سازگار با Importer دارد؛ با خطاهای SKU، variation و URL تصویر مشکل دارد.
- معیار: با اجرای تستی در سایت آزمایشی، CSV درست بارگذاری شود؛ محتوای تصویر/قیمت مطابق منبع باشد.

### پرسونای C: اپراتور داخلی کارمند من

- در پایلوت کیفیت داده، هزینه، خطای AI، درخواست حذف و اعتبار را بررسی می‌کند.
- معیار: بتواند خطا را با Audit Trail حل کند و عملیات کاربر را بدون دستکاری مخفی داده‌ها دنبال کند.

### سناریوی نمونه E2E

1. کاربر `/start` می‌زند؛ رضایت‌نامه و محدودیت‌ها را می‌بیند؛ Workspace ساخته می‌شود و اعتبار هدیه **فقط یک بار** تخصیص می‌یابد.
2. ربات نام برند، گروه محصول، واحد قیمت (پیش‌فرض قابل تغییر **تومان**)، لحن، مخاطب، لوگو و خروجی‌های مطلوب را می‌پرسد. اجازه می‌دهد بعداً تکمیل شود.
3. ربات خلاصه پروفایل را برای **تأیید** نشان می‌دهد. آشنایی پایه اعتبار مصرف نمی‌کند.
4. کاربر می‌گوید «محصولات جدید» و ۷ عکس + ویس + CSV قیمت می‌فرستد؛ دکمه **«ارسال تمام شد»** را می‌زند.
5. سیستم فایل‌ها را در پروژه نگه می‌دارد، تصاویر را به اقلام احتمالی نسبت می‌دهد، داده را استخراج می‌کند و **موارد ناسازگار** را پررنگ می‌کند.
6. ربات: «۸ قلم احتمالی شناسایی شد؛ قیمت ۲ قلم مشخص نیست و ۱ عکس ممکن است تکراری باشد. اجازه می‌دهید در یک صفحه بررسی کنیم؟»
7. مشتری ابهامات را رفع و **جدول محصول** را تأیید می‌کند.
8. ربات «CSV + کاتالوگ PDF + لینک آنلاین» را پیشنهاد می‌دهد؛ هزینه/اعتبار را پیش از پردازش پرهزینه نشان می‌دهد؛ کاربر خروجی‌ها و هزینه را تأیید می‌کند.
9. اعتبار رزرو، پردازش صفی و پیش‌نمایش تولید می‌شود. خطاهای قابل جبران توسط سیستم بدون هزینه دوباره رفع می‌شوند.
10. پس از تأیید نهایی، اعتبار مصرف قطعی و خروجی‌ها از تلگرام + آرشیو قابل دریافت می‌شوند؛ رکورد محصولات با نسخه در Repository باقی می‌ماند.
11. هفته بعد مشتری می‌گوید «از همان ۸ قلم، کاتالوگ بدون قیمت بساز». سیستم از داده قبلی و حافظه برند استفاده می‌کند، بدون تکرار استخراج.

## ۴. نیازمندی‌های کارکردی به‌تفکیک Epic

### E01 — هویت و Workspace | P0

**شرح:** ثبت‌نام مبتنی بر Telegram User ID، ساخت یک Workspace و اتصال کارمند اول.

| ID | Requirement | معیار پذیرش (Acceptance Criteria) |
|---|---|---|

### E04 — موتور استخراج، خوشه‌بندی و تطبیق | P0

### E06 — خروجی‌ها و کتابخانه محصولات | P0

**الف) Product Repository:** هر کالای تأییدشده یک رکورد مستقل از Batch دارد؛ `product_revision` تغییرات آینده را ثبت می‌کند. حذف از PDF به معنی حذف از Repository نیست.

**ب) خروجی‌های قطعی P0:**

1. **Structured JSON:** schema داخلی نسخه‌دار؛ با مستندات و نشانگر وضعیت تأیید؛ **قول Import مستقیم JSON به ووکامرس داده نشود**.
2. **WooCommerce CSV:** فاز اول `simple products` با ستون‌های واقعی `Type`, `SKU`, `Name`, `Published` (اگر مناسب), `Description`, `Short description`, `Regular price`, `Categories`, `Images`, `Attribute N...` در صورت معتبر بودن. قالب باید مطابق importer نسخه تست‌شده باشد؛ نام ستون‌ها و نمونه واقعی از فروشگاه staging استخراج و تست شوند.
3. **PDF Catalog:** فارسی راست‌به‌چپ، ۱ تا ۲ قالب ثابت، لوگو/نام/تصویر/مشخصات/قیمت اختیاری، شماره صفحه، تاریخ ایجاد و نسخه؛ UTF-8 و فونت مجاز؛ رندر deterministic.
4. **Online Catalog:** صفحه HTTPS با URL تصادفیِ دشوارحدس، حداقل metadata و تنظیم عمومی/خصوصی، فعال/غیرفعال، نسخه immutable یا لینک ثابت به آخرین نسخه، انقضا اختیاری؛ عدم ایندکس پیش‌فرض برای کاتالوگ‌های غیرعمومی.
5. **ZIP:** بسته اختیاری شامل CSV، JSON، تصاویر و راهنمای واردسازی؛ لینک دانلود مجدد با مجوز.

**ج) خروجی‌های P1:** تصاویر بهینه‌سازی‌شده (حذف پس‌زمینه/اصلاح نور با حفظ ماهیت کالا)، استوری 9:16 مبتنی بر قالب ثابت، کپشن، فهرست قیمت/کاتالوگ بدون قیمت، ویرایش دسته‌ای، محصول متغیر با تست اختصاصی.

**نکته حساس تصاویر ووکامرس:** ستون `Images` در Importer غالباً به URL قابل دسترسی نیاز دارد. URL کوتاه‌عمرِ خصوصی ممکن است هنگام import یا استفاده بعدی خطا بدهد. در MVP یا تصاویر را با **رضایت صریح** روی URL عمومی پایدارِ صادراتی در بازه معلوم میزبانی کنید، یا **CSV بدون image URL + بسته ZIP و راهنمای بارگذاری** بدهید؛ هرگز نگویید ZIP به‌تنهایی خودکار تصاویر را به importer وصل می‌کند. لینک عمومی باید قابل لغو و دارای شرایط نگهداری روشن باشد.

## ۵. تجربه مکالمه و UX Contract

### اصل تعامل

- پیام‌های کوتاه، فارسی ساده، **یک تصمیم اصلی در هر پیام**؛ در پایان هر مرحله «بعداً»، «برگشت» و «اصلاح» موجود باشد.
- سؤال فقط درباره ابهامی که مانع خروجی درست می‌شود؛ سایر موارد با مقدار «نامشخص» یا پیش‌فرض تأییدشده.
- ربات از انجام قطعیِ کار تا قبل از پایان واقعی job ادعای موفقیت نکند.
- کاربر بتواند «این‌ها تمام شد»، «اول پیش‌نمایش»، «مثل دفعه قبل»، «بدون قیمت» را بیان کند.

### Conversation intents اولیه

`START`, `SETUP_BRAND`, `EDIT_BRAND`, `NEW_PROJECT`, `ADD_ASSETS`, `FINISH_UPLOAD`, `ANSWER_CLARIFICATION`, `REVIEW_PRODUCTS`, `QUOTE_EXPORT`, `CONFIRM_EXPORT`, `STATUS`, `GET_OUTPUT`, `LIST_PROJECTS`, `CANCEL`, `BALANCE`, `PRIVACY_DELETE`, `SUPPORT`, `FALLBACK`.

### رفتار Ambiguity / Interruption

- اگر پیام برای دو پروژه ممکن است: نام پروژه‌ها را پیشنهاد بده؛ بی‌اجازه به پروژه نچسبان.
- اگر کاربر وسط Batch می‌گوید «موجودی» و intent مشخص نیست: سؤال جهت‌دار بده.
- Voice transcription کم‌اطمینان را **به نقل از کاربر** نمایش بده و تأیید بخواه.
- اگر مدل پاسخ نامربوط/مخاطره‌آمیز داد، از متن قالب کنترل‌شده و اپراتور استفاده کن.

## ۶. State Machine و قرارداد وضعیت‌ها

```text
NEW
  -> COLLECTING_INPUT
  -> EXTRACTING
  -> NEEDS_CLARIFICATION <-> EXTRACTING
  -> REVIEW_REQUIRED
  -> PRODUCT_APPROVED
  -> QUOTED
  -> CREDIT_RESERVED
  -> GENERATING
  -> OUTPUT_REVIEW_REQUIRED
  -> COMPLETED

From eligible states -> CANCELLED
GENERATING -> RETRYABLE_FAILURE -> GENERATING / FAILED
QUOTED -> EXPIRED -> QUOTED
```

**Invariantها:**

- `PRODUCT_APPROVED` باید snapshot/version مشخص داشته باشد.
- `CREDIT_RESERVED` بدون Quote معتبر و موجودی کافی ممنوع.
- `COMPLETED` فقط وقتی فایل‌ها موجود، valid و قابل تحویل باشند.
- `FAILED` بدون log و خطای قابل توضیح مجاز نیست.
- دریافت Telegram update تکراری نباید Transition تکراری ایجاد کند.
- Approval کاربر نسبت به version قبلی پس از تغییر رکورد معتبر نیست.

**وضعیت هر محصول:** `DRAFT_EXTRACTED`, `NEEDS_REVIEW`, `APPROVED`, `ARCHIVED` مستقل از پروژه.

## ۸. معماری پیشنهادی (Modular Monolith با استاندارد Action/Repository/Service)

```text
Telegram Bot (webhook)      Review Web View (small, optional P1)
          |                         |
          +------------+------------+
                       v
                 Auth / API Layer
                       |
       +---------------+--------------------+
       |               |                    |
 Workspace/Memory   Product Domain     Wallet/Billing
       |               |                    |
       +---------------+--------------------+
                       |
               Workflow Orchestrator
                       |
             Job Queue / Worker Pool
          +------------+------------+
          |            |            |
      AI Adapters   Exporters   Media Pipeline
          |            |            |
       Model APIs   CSV/PDF/HTML   Image/Audio
          +------------+------------+
                       |
         PostgreSQL + Object Storage + Redis
                       |
           Audit / Monitoring / Admin
```

**تصمیم Stack برای MVP:** **Laravel 13.x + PHP 8.4 + PostgreSQL 17 + Redis 7.2 + n8n 2.44.6 (stable مبنای ۲۶ اکتبر ۲۰۲۶)**؛ Backend به‌صورت Modular Monolith و مالک داده/مجوز/پول، n8n فقط Workflowهای AI. استقرار با Docker Compose v2 روی Ubuntu 24.04 LTS؛ Caddy 2 برای HTTPS و PHP-FPM؛ Object Storage خصوصی S3-compatible؛ Horizon برای صف Laravel. خروجی PDF فارسی با HTML/CSS RTL و Chromium/Playwright در worker ایزوله، مشروط به تست فونت. جزئیات، پیش‌نیازها و سیاست پین نسخه در Runbook مستقل آمده است. داده اصلی در n8n نگهداری نمی‌شود؛ Python worker فقط در صورت نیاز اثبات‌شده افزوده شود.

**قاعده ساختار و کیفیت کد:** `Karmandeman_Engineering_Standards_v1.0.md` قرارداد الزام‌آور است: `app/Actions/{Feature}` برای use caseها، Controllerهای نازک در `Http/Controllers/API/V1`، اعتبارسنجی در `Http/Requests/{Feature}`، خروجی در `Http/Resources/{Feature}`، قرارداد Persistence در `Repositories/Contracts` و پیاده‌سازی در `Repositories/Eloquents/{Model}`، orchestration/integration در `Services`، binding در `Providers`، model سبک و Vue 3 + TS به‌صورت feature-first در `resources/js/src/modules`. ساختن `app/Domain` به‌عنوان جایگزین ساختار بالا در این پروژه ممنوع است. **اصل عدم overengineering:** در P0 نیازی به microservices، Kubernetes، vector database یا orchestration چندایجنتی نیست. حافظه صریح برند را از PostgreSQL بگیرید؛ اگر حجم دانش نیاز به بازیابی معنایی پیدا کرد، pgvector را بعداً اضافه کنید.

## ۹. امنیت، حریم خصوصی و عملیات در ایران

### ۹.۱ کنترل‌های الزام‌آور

- **Telegram Webhook:** secret token، HTTPS، rate limit و deduplication بر اساس `update_id`. Token Bot در log/خطا/URL نمایش داده نشود.
- **Mini App:** `initData` با الگوریتم رسمی در Backend verify شود؛ `auth_date` منقضی و replay مهار شود؛ `initDataUnsafe` قابل اعتماد نیست.
- **Tenant isolation:** هر Read/Write/Download با `workspace_id` اجباری؛ تست نفوذ بین دو Workspace.
- **File safety:** MIME sniffing، size quota، بررسی فایل مخرب، SVG/HTML غیرمجاز، macroهای XLSX اجرا نشوند، decompression bomb کنترل شود، فایل‌های مشتری در bucket خصوصی.
- **Prompt-injection protection:** متن ورودی عکس، PDF، اسناد و پیام‌ها **داده غیرقابل اعتماد** هستند؛ دستور کاربر/سیستم را override نکنند؛ AI tool permission محدود به Task مجاز.
- **Sensitive commercial data:** فروشنده مشخص کند کدام خروجی عمومی است؛ قیمت تأمین‌کننده/لیست عمده بدون تأیید منتشر نشود.
- **Public catalogs:** Token غیرقابل حدس، revoke، جلوگیری از index پیش‌فرض، نسخه‌بندی، انقضا و Rate Limiting؛ دسترسی عمومی عامدانه است نه اتفاقی.
- **Data deletion:** حذف حساب/برند/فایل با عملیات قابل ردیابی و چرخه حذف نسخه‌ها/مشتقات/embedding (اگر وجود دارد) و بکاپ مطابق سیاست منتشرشده.
- **Audit & Support:** دسترسی‌های اپراتور Role-based، trail غیرقابل ویرایش، توضیح برای refund/credit adjustment.
- **Provider risk:** امکان جایگزینی AI provider، آگاه‌سازی مشتری از پردازش احتمالی داده توسط ارائه‌دهنده ثالث، بررسی محل پردازش، حقوق قراردادی و ریسک دسترسی/تحریم قبل از عرضه.

### ۹.۲ ملاحظات ایران

- تلگرام در ایران ممکن است بدون دسترسی پایدار نباشد؛ نرخ شکست/رهاشدن را بر اساس دستگاه و شبکه اندازه بگیرید؛ کانال وب آینده باید از آغاز قابل افزودن باشد.
- قیمت‌ها به تومان یا ریال دریافت می‌شوند؛ واحد ورودی را **هر بار** و در منبع نگه دارید؛ «مبلغ ۵۰۰» بدون واحد باید سؤال ایجاد کند.
- فارسی RTL، اعداد محلی، تقویم شمسی (نمایش)، نام‌های محاوره‌ای، نیم‌فاصله و نگاشت ی/ک باید تست شوند.
- حقوق مصرف‌کننده، پرداخت، مالکیت تصاویر، حریم خصوصی و شرایط AI provider با مشاور حقوقی محلی بررسی شود؛ این PRD مشاوره حقوقی نیست.

| Contribution per customer | درآمد تحقق‌یافته − مدل/پردازش/فایل/پرداخت/پشتیبانی متغیر | اقتصاد واحد |

| Data reuse ratio | خروجی‌های استفاده‌کننده از محصول موجود / همه خروجی‌ها | ارزش Repository و حافظه |

**تعریف استفاده واقعی:** دانلود به‌تنهایی شاخص ضعیفی است. برای CSV، از مشتری بخواهید نتیجه Import را گزارش دهد یا در پایلوت با اجازه صحت آن را روی staging مشاهده کنید؛ برای کاتالوگ، ارسال به خریدار/بازخورد را با نمونه‌گیری مصاحبه‌ای بررسی کنید.

## ۱۶. پروتکل پایلوت و Gateهای تصمیم

### طراحی پایلوت

- **گروه هدف:** ۵–۱۰ فروشگاه کوچک/متوسط، ترجیحاً کیف/اکسسوری؛ حداقل ۲ با WooCommerce و حداقل ۲ موبایل‌محور بدون اپراتور سایت.
- **نمونه کاری:** چند Batch واقعی در دو نوبت جدا؛ صرفاً دموی زیبا کافی نیست.
- **پشتیبانی:** انسان در جریان، ثبت دقیق دقایق کمک و دلیل مداخله؛ هیچ اصلاح پنهانی که سنجه خطای AI را مخدوش کند.
- **مصاحبه:** ۱۰ دقیقه پس از اولین خروجی و ۳۰ روز بعد؛ شاهد استفاده واقعی را جمع‌آوری کنید.

### اهداف داخلی اولیه، قابل بازنگری

| Gate | پیشنهاد تصمیم | آستانه راهنما* |
|---|---|---|
| G1: Feasibility | مسیر را ادامه بده/کوچک کن | ≥۸۰٪ اقلام در تست پس از بررسی انسانی قابل تحویل شوند؛ نه الزاماً بدون اصلاح |
| G2: Usability | ساده‌سازی یا اصلاح UX | اکثر کاربران پایلوت بتوانند با راهنمایی محدود نخستین پروژه را کامل کنند |
| G3: Product value | ساخت وب یا توقف | ≥۵ مشتری از خروجی در کار واقعی استفاده کنند؛ شواهد مشاهده/تأییدشده |
| G4: Repeat | ارزش تکرار یا پروژه‌ای؟ | سفارش دوم در ۳۰–۶۰ روز برای بخش معنی‌دار مشتریان تکرارشونده |
| G5: Economics | قیمت‌گذاری و دامنه | مسیر قابل دفاع به Contribution Margin مثبت پس از Support |
| G6: Payment | عرضه پولی | کانال تسویه/پرداخت مجاز و واقعاً قابل استفاده برای مشتری ایرانی |

`*` این معیارها **هدف‌های فرضی مدیریت محصول** هستند؛ نمونه کوچک و فصلی‌بودن ورود کالا باعث می‌شود تصمیم فقط با درصدها گرفته نشود. تصمیم نهایی با شواهد کیفی و کمی مشترک.

### تصمیم‌های ممکن

- **Proceed:** خروجی مفید، هزینه قابل کنترل، نشانه استفاده تکراری؛ توسعه Review Web Product.
- **Pivot:** خروجی استفاده می‌شود ولی پرداخت/تکرار در کاتالوگ ضعیف؛ بررسی صنف/Workflow مانند استعلام B2B.
- **Stop:** خطای دادهٔ تجاری غیرقابل کنترل یا نیاز به مداخله پرهزینه برای هر سفارش.

## ۱۷. معیار آمادگی برای توسعه پنل وب

وب‌اپ کامل صرفاً «زمانی که ربات تکمیل شد» ساخته نمی‌شود؛ باید **مسئله تأییدشده** داشته باشد:

- مشاهده مکرر نیاز به بررسی دسته‌ای، مقایسه تصویر اصلی و فیلد استخراج‌شده؛
- چند ده یا چند صد محصول در Repository مشتری؛
- نیاز به ویرایش گروهی و تاریخچه تغییرات؛
- چند پروژه/خروجی از داده قبلی و درخواست اتصال مستقیم؛
- داده‌ای که نشان می‌دهد وب‌پنل نرخ خطا/زمان بررسی را کاهش می‌دهد.

وب باید **همان حساب، حافظه، محصول، پروژه، خروجی و اعتبار** را مصرف کند. Migration محصول از ربات به وب **نباید** شامل ارسال دوباره عکس و شروع مجدد حافظه باشد.

### ADR-001 — Laravel مالک هسته محصول، n8n صرفاً موتور AI

- **تصمیم:** Laravel 13.x / PHP 8.4 پیاده‌سازی API، Identity، Workspace، Brand Memory، Product Repository، Project/Task State Machine، approvals، wallet_ledger، audit، export و Telegram adapter را بر عهده دارد. n8n فقط orchestration ماژولار گردش‌کارهای تشخیص صوت، استخراج تصویر، matching، clarification، متن و QA مبتنی بر مدل را انجام می‌دهد.
- **الگوی اجرا:** Telegram → Laravel Webhook (تأیید secret + dedup) → ثبت immutable event / پروژه → Laravel Horizon Job → فراخوانی workflow داخلی n8n با `run_id`, `project_id`, `workflow_version`, `input_asset_ids` → دریافت JSON ساختاریافته و امضاشده از n8n → اعتبارسنجی مجدد و ذخیره در Laravel → تأیید کاربر → صدور خروجی.
- **مرز مالکیت:** n8n حق نوشتن مستقیم در جداول کسب‌وکار/کیف پول را ندارد و DB اصلی برنامه را نمی‌خواند؛ داده را فقط از API داخلی scoped با مجوز حداقلی دریافت می‌کند. در اجرای AI خروجی schema-validated اما هنوز **untrusted** است. مدل اجازه تغییر قیمت قطعی، تأیید داده، انتقال اعتبار یا انتشار را ندارد.
- **کنترل هزینه:** برای هر run سقف token/زمان/تعداد درخواست مدل تعریف شود؛ provider tokens، latency، retry count، output acceptance و estimated actual cost در Laravel جمع‌آوری شوند.
- **استاندارد قرارداد:** workflow ورودی/خروجی versioned JSON Schema، UUID برای correlation، idempotent callback، timeout و retry محدود. Workflow JSONها بدون credential در Git نگهداری شوند.
- **شرط مجوز:** قبل از paid pilot، مدل استفاده backend از n8n با مفاد مجوز رسمی n8n بررسی و در صورت ابهام تأیید کتبی اخذ شود. مشتری مستقیماً n8n یا workflow builder آن را دریافت نمی‌کند.

### ADR-002 — پایه نسخه‌های انتخاب‌شده

| جزء | تصمیم MVP | قاعده ارتقا/توضیح |
|---|---|---|
| Laravel | **13.x**، `composer.json: ^13.0` | در `composer.lock` نسخه واقعی ثبت؛ امنیت Laravel 13 تا مارس ۲۰۲۸؛ Patch/Minor کنترل‌شده در CI |
| PHP | **8.4.x FPM** | تصویر `php:8.4-fpm-alpine` در زمان انتشار با **digest** پین شود؛ Laravel 13 از PHP 8.3–8.5 پشتیبانی می‌کند |
| PostgreSQL | **17.11** baseline | تصویر PG17.11 در staging تست و سپس با digest پین؛ پایگاه n8n مجزا از پایگاه Laravel؛ `pgvector` فعلاً خارج P0 |
| Redis | **7.2.x** | برای Queue/Cache/Rate limiting؛ ترجیح image ثابت `redis:7.2-alpine` + digest، persistence policy روشن |
| n8n | **2.44.6 stable baseline** | `docker.n8n.io/n8nio/n8n:2.44.6`، نه `latest` یا beta؛ قبل deploy digest و health/compatibility verify؛ انتشار بعدی ممکن است نسخه را تغییر دهد |
| OS | **Ubuntu Server 24.04 LTS** | x86_64، به‌روزرسانی امنیتی خودکار و Host firewall |
| Container runtime | **Docker Engine از مخزن رسمی + Compose Plugin v2** | نسخه نصب‌شده در manifest عملیات ثبت و در staging تست شود، auto-upgrade خودکار ممنوع |
| TLS edge | **Caddy 2.x** | HTTPS خودکار، reverse proxy، بدون مواجهه عمومی DB/Redis/n8n editor |
| PHP background | **Laravel Horizon** | worker جدا با Redis و restart در deploy؛ scheduler جدا با `schedule:work` |
| PDF | **Chromium/Playwright renderer مستقل** | نسخه Node **24 LTS** و مرورگر سازگار با lockfile پین؛ PDF فارسی/RTL با فونت دارای مجوز مناسب |
| Object storage | **S3-compatible private bucket** | bucket جدا برای originals/outputs/public versions؛ access key محدود، signed URL و lifecycle |

**نکته:** شماره‌های بالا «baseline تصمیم» در زمان نگارش‌اند؛ رشته‌های tag مبنای build هستند و **پین نهایی production باید به digest تصویر حل‌شده و ثبت‌شده در Release Manifest تبدیل شود**. هر ارتقای نابرنامه‌ریزی‌شده ممنوع.

### ADR-003 — Docker Compose پایلوت؛ نه Kubernetes

- **استقرار نخستین:** یک VPS دارای ۴ vCPU، ۸ GiB RAM و حدود ۸۰–۱۲۰ GiB SSD برای pilot کم‌حجم، در صورت استفاده از Object Storage بیرونی و سقف هم‌زمانی؛ این‌ها برآورد اولیه ظرفیت‌اند نه تضمین عملکرد. فایل‌های تصویری حجیم و PDF rendering می‌توانند نیاز را بالا ببرند.
- **سرویس‌ها:** `web` (Caddy)، `app` (PHP-FPM)، `horizon`، `scheduler`، `postgres_app`، `postgres_n8n`، `redis`، `n8n`، و `pdf-renderer` (پس از اتصال ماژول). Node build فقط برای assets/renderer است؛ Node server برای Backend نیاز نیست.
- **Network:** تنها TCP/80,443 عمومی؛ SSH فقط با کلید و محدودیت IP/VPN؛ DB/Redis/n8n ports روی اینترنت پابلیک نشوند. ادیتور n8n فقط در شبکه خصوصی یا از تونل مدیریتی ایمن قابل دسترسی باشد.
- **Storage:** Volume پایدار برای PostgreSQL و n8n؛ داده مشتری/تصویر/خروجی در Object Storage مستقل؛ کانتینرهای برنامه immutable و قابل rebuild؛ نسخه DB بدون backup/restore آزمایش‌شده ارتقا نیابد.
- **توسعه آینده:** مهاجرت به سرور DB/worker مستقل و Load Balancer فقط بعد از معیارهای فشار واقعی؛ Compose خودبه‌خود High Availability ایجاد نمی‌کند.

### ADR-004 — امنیت، فایل و دسترسی AI

- Telegram webhook با `X-Telegram-Bot-Api-Secret-Token`، dedup `update_id` و پاسخ سریع `2xx`; پردازش سنگین در Queue.
- n8n فقط از طریق API داخلی Backend با `service identity` کم‌دسترسی و TTL کوتاه به اطلاعات **ضروری** پروژه دسترسی دارد؛ callback باید authenticated، scope-bound و idempotent باشد. n8n نباید مستقیماً فایل‌های دلخواه مشتری را از URLهای نامطمئن fetch کند (SSRF).
- Credentials مدل‌ها در n8n با کلید رمزگذاری پایدار و secrets خارج Git؛ execution history فاقد داده خام حساس در حالت عادی؛ pruning، audit، export/backup workflow و rotation تدوین شود.
- backup رمزگذاری‌شده **خارج از سرور** برای هر دو PostgreSQL، Object Storage و secrets موردنیاز recovery؛ restore drill پیش از pilot. هدف داخلی اولیه **RPO ≤ 24h / RTO ≤ 8h** فقط بعد از آزمون عملی اعلام شود.
- health checks، structured JSON logs با `correlation_id` بدون محتوای حساس، خطای worker، n8n failure، هزینه AI و مانده اعتبار پایش شوند.
- برای ادغام NextPay، سیاست Stars تلگرام و مجوز ارائه‌دهنده AI/زیرساخت، Gate مستقل Go/No-Go اعمال شود؛ راهکار پرداخت بدون تأیید سازگاری اجرا نشود.

### ADR-005 — ساخت، تست، انتشار و بازگشت

1. branch protection، pull request و code review؛ `composer.lock`، `package-lock.json` و workflow JSONهای sanitized در Git؛ `.dockerignore` در root قبل از build الزامی و `.env.production` خارج context یا مستثنا است.
2. CI: `composer validate`، lint/format، static analysis، unit/integration tests، schema contract tests، security scan/secret scan و ساخت تصاویر immutable.
3. در staging: migration آزمایشی، E2E تلگرام، دانلود فایل، PDF فارسی، Woo CSV importer، wallet idempotency، خطا/timeout n8n و tenant isolation.
4. پیش از production: backup تازه + آزمون restore قبلی؛ deploy image با tag نسخه Release + digest؛ `php artisan migrate --force` برای migration سازگار با نسخه قبل؛ `php artisan optimize`؛ `php artisan horizon:terminate` برای بارگیری worker جدید.
5. smoke test `/up` و probe وابستگی‌ها، Telegram webhook info، یک Workflow AI و یک خروجی آزمایشی؛ در failure، بازگشت image و workflow **فقط اگر Schema دیتابیس backward compatible است**. در غیر این صورت forward-fix/restore تحت برنامه توقف سرویس.
6. عملیات استقرار و دسترسی با audit؛ حداقل dev، staging، production با bot token، دیتابیس، bucket و اسرار جداگانه.

### ADR-006 — وضعیت تصمیم و موارد باز باقی‌مانده

**قطعی برای شروع Development:** Laravel13/PHP8.4، n8n داخلی، PostgreSQL17، Redis7.2، Docker Compose/Ubuntu24.04، Caddy/HTTPS، نگهداری فایل مستقل، API-first، نسخه‌کردن schema، private DB/Redis، deployment pipeline و backup policy.

**پیش‌نیاز قبل از اولین استقرار:** انتخاب و تست میزبان از نظر دسترس‌پذیری کاربران ایرانی و مجوز providerها؛ دریافت دامنه/TLS و Object Storage مناسب؛ ایجاد Bot Token و Secret؛ resolve image digests؛ تعیین سقف هزینه مدل و نگهداری فایل؛ نتیجه بررسی n8n license؛ تصمیم کانال پرداخت؛ تست PDF فارسی با فونت دارای حق استفاده؛ اجرای restore drill.

**مستند اجرایی الزام‌آور:** `Karmandeman_Deployment_Runbook_v1.1.md` شامل topology، نام سرویس‌ها، متغیرهای محیطی، Runbook عملیات، روش بکاپ/ریستور، مقیاس، هشدارها و چک‌لیست انتشار است.

## ۲۴. ADR-007 — استاندارد اجباری Laravel و Vue برای تمامی Featureهای MVP (نسخه ۱.۳)

**تصمیم:** ساختار پروژه User-approved و سند `Karmandeman_Engineering_Standards_v1.0.md` از آغاز implement **الزام‌آور** است و بر هر عبارت قدیمی/مبهم درباره `app/Domain` یا Controllers حاوی query اولویت دارد. این قرارداد مستقل از انتخاب n8n است.

### ۲۴.۱ پوشه‌های Backend الزام‌آور

```text
app/Actions/{Identity,Workspace,Brand,Memory,Product,Project,Approval,Catalog,Wallet,Employee}/
app/Http/Controllers/API/V1/{feature}/       # thin controllers
app/Http/Controllers/Webhooks/               # Telegram, n8n callback, payment; authenticated
app/Http/Requests/{feature}/                 # Form Requests
app/Http/Resources/{feature}/                # API Resources
app/Models/                                  # Eloquent only
app/Repositories/Contracts/                 # interfaces
app/Repositories/Eloquents/{Model}/          # Eloquent implementations
app/Services/{AI,Telegram,Memory,ProductIntake,Export,Storage,Billing}/
app/Providers/                               # Repository DI bindings
app/Scopes/                                  # reusable global Eloquent scopes
app/Helpers/                                 # pure utilities only
resources/js/src/modules/{auth,brand,memory,product,project,catalog,wallet,employee,admin}/
resources/js/src/shared/{components,composables,types,utils,api}/
resources/js/src/stores/; resources/js/src/router/
```

`Jobs/`, `Policies/`, `Events/`, `Enums/` و `Data/` در صورت نیاز جزء مکمل هستند و ممنوع نیستند. **هر Feature** Action/Request/Resource اختصاصی دارد؛ Controller فقط delegate و transform می‌کند. API domain logic در Vue یا n8n تکرار نشود.

### ۲۴.۲ نمونه نگاشت الزام‌آور

`POST /api/v1/projects` → `Project/CreateProjectRequest` → `API/V1/Project/ProjectController@store` → `Project/CreateProjectAction::execute()` → `ProjectRepositoryInterface` → `Eloquents/Project/EloquentProjectRepository` → `ProjectResource`. اجرای n8n از Job after-commit و orchestration service انجام می‌شود، نه از Controller. `ApproveMemoryCandidateAction` مسئول ارتقای حافظه به وضعیت تأییدشده است و استخراج AI هرگز مستقیماً item فعال ایجاد نمی‌کند. `ReserveCreditsAction` + `CaptureCreditsAction` دو use case جدا هستند و در تراکنش با idempotency اجرا می‌شوند.

### ۲۴.۳ شرط پذیرش قابلیت برای تیم توسعه

- همه API endpointهای عمومی خروجی Resource یکنواخت و خطای ساختاریافته دارند؛ تست قرارداد API موفق است.
- `FormRequest`، `Policy` و `workspace_id` scoping با تست‌های مثبت و منفی tenant isolation پوشش داده شده‌اند.
- Actionها کوچک، typed و تک‌مسئولیتی‌اند؛ Repo contract در Service Provider bind و مستقل تست شده است.
- Laravel Pint، PHPStan/Larastan، PHPUnit/Pest و اسکن secrets در CI اجرا می‌شوند؛ `composer.lock` و lockfile frontend موجود است.
- Frontend وب سبک MVP و پنل وب آینده از Vue 3 + TypeScript + Pinia + Vue Router و feature modules استفاده می‌کند؛ ESLint، typecheck و تست UI اجرا می‌شوند.
- تغییر معماری بدون ثبت ADR، Code Review و migration تست‌شده مجاز نیست؛ فایل الگوی infra فقط قرارداد است، نه مدرک اجرای این کنترل‌ها.
